### Blockers

1. `templates/entity/new/backend/use-cases/list.ejs.t:151,155` with `templates/entity/new/backend/use-cases/search.ejs.t:60`.
   **A child's search is always child-rooted, whether or not a filter is set.** The search use case always passes
   `{ where: rowFilter }`. The closure returns `and()` (which is `undefined`) when no filter is set, but the closure
   itself is always defined. S5 makes `whereClause !== undefined` the routing decision, so a defined closure now means
   "a filter applies". An empty input is read as a present one (CLAUDE.md gate rule (c), inverted; `convenient_fallback`).
   **Scenario:**
   - `GET /meetings/search?sort_by=occurred_at` with no filter returns a 400 `sort_not_combinable`: "…cannot be
     combined with this filter in v1". There is no filter.
   - `GET /meetings/search` with no params sorts `id desc`, while `GET /meetings` sorts `created_at desc, id desc`.
   - The generated search controller's own doc (`search-controller.ejs.t:29`) says search "pages and sorts exactly as
     `GET /meetings` does (#744)". That is now false for a child.
   - The scaffold test (`test/scaffold/tests/inheritance-http.test.ts:201-216`) only tries the filtered case.

   **Fix:** in `search.ejs.t`, decide from `searchInput` whether any declared filter is set, and pass `where` only then
   (e.g. `{ where: hasFilter ? rowFilter : undefined }`). For a non-child an undefined `where` and an empty one read
   the same, so the change is safe for every entity. Add an unfiltered `sort_by=<base column>` case and an unfiltered
   default-order case to the scaffold test.

### Should-fix

1. `src/derived/api/entity.ts:894-897`, `templates/entity/new/backend/use-cases/delete.ejs.t:40`.
   **The derived surface records a delete pre-read that the generated code does not make.** Every delete use case
   gets `alsoCalls: [findById | findWithBase]`, but the template prints the pre-read only in its
   `hasEmits && deleteEventType` branch. All 15 baseline delete use cases call only `service.delete`
   (`test/baseline/packages/api/src/modules/accounts/use-cases/delete-account.use-case.ts`). Yet every entity snapshot
   under `test/api-surface-golden/snapshot/` gained an `alsoCalls` entry. For example, `account.json` says
   `DeleteAccountUseCase` also calls `AccountService.findById`, and Studio prints that call
   (`tools/studio/src/inspector/surface-view.ts:221`). This is the surface-as-projection rule broken in the
   listed-but-not-emitted direction, which no gate checks: `api-surface-parity.test.ts` does not read use-case refs.

   Related problems:
   - The child list's `alsoCalls` (`entity.ts:856-860`) is never read by `list.ejs.t`. The template finds `listFlat`
     by kind and hardcodes `this.service.list` and `this.service.count`, so the declaration and the print can drift
     apart.
   - The delete template reads `alsoCalls[0]` by position.
   - No child fixture declares `emits:`, so the one branch that prints the child's `findWithBase` pre-read (round 3's
     fix #1) is not generated by any gate.

   **Scenario:** a reader of the golden or of Studio's use-case panel sees a pre-read that `DeleteAccountUseCase` does
   not do. Adding a second `alsoCalls` entry ahead of the pre-read silently changes which method an emitting delete
   calls.

   **Fix:**
   - Give the pre-read its own named field (e.g. `preRead?: MethodRef`), recorded only when the delete emits an event.
     The derivation needs that input; the delete event's existence lives in `prompt.js` today.
   - Have `delete.ejs.t` print that field.
   - Have `list.ejs.t` print `list`, `count`, `listFlat` and `countFlat` from the use case's own refs.
   - Extend the parity gate to use-case call refs.
   - Add a child fixture with a delete event, so the flat pre-read compiles somewhere.

2. `templates/entity/new/backend/entity-locals.js:2660-2664`, `templates/entity/new/backend/controller.ejs.t:263-265`,
   `templates/_shared/inheritance.mjs:382` — **DECISION**.
   **`kind_requires_child` and its `createPath` can never reach an HTTP client.** The base's create DTO narrows the
   discriminator to `z.enum(baseOnlyKinds)`. So `ZodValidationPipe` refuses `POST /communications {"kind":"meeting"}`
   with `{ message: 'Validation failed', issues: [invalid_enum_value] }`, before `assertBaseOnlyKind` runs. The
   controller's `kind_requires_child` mapping is never answered by a generated route.
   - The mapping's only test stubs the use case (`inheritance-http.test.ts:389-416`).
   - The real-route test (`:328-337`) asserts only `status === 400`, so it cannot tell which layer refused.
   - `KindImmutableError` and `KindMismatchError` cannot be reached through the generated routes either, because the
     DTOs strip `kind`.

   The S5 change of `createPath` from `MeetingService.create` to `POST /meetings` makes things worse for the only
   callers who do receive it:
   - In-process callers of `CommunicationService.create` / `upsertByNaturalKey` are now handed an HTTP route.
   - For `upsertByNaturalKey` that route is not even the matching operation: the child has its own
     `upsertByNaturalKey`.
   - The route is built outside the derivation (`POST ${routePath(ref.plural)}`, against ADR-046), not read from the
     child's derived routes. A child with `api: false` or `generate.writes: false` would be named by a route that does
     not exist.
   - `src/__tests__/runtime/base-classes/inheritance-writes.spec.ts:84-93` still uses the old `Service.create` format.

   **Scenario:** a client that posts a child kind to the base gets a generic enum-validation 400 with no route. A
   server-side caller of `upsertByNaturalKey({ kind: 'email' })` is told to "create it through POST /emails".

   **Fix (Doug's call):**
   - (a) Keep the DTO's full enum and let the service guard answer, so the 400 carries `code` and the route, and the
     rule has one owner.
   - (b) Keep the narrow enum, put `createPath` back to the in-process method, and delete the controller mappings
     that cannot be reached.
   - (c) Keep the narrow enum and give it an error message that names the child's route.

   Whichever you choose, read the child's create route from its derived surface (`http.routes`, kind `create`) and
   leave it absent when that route does not exist.

3. `templates/entity/new/backend/dto/output.ejs.t:13-34` vs `:43-64`. **The output DTO's body is copied into both
   branches.** The same 20-line object (id, FKs, fields, `externalId`, timestamps, `deletedAt`) appears twice. The
   branches differ only in the export name. `dto/create.ejs.t` has the same shape at a smaller size: its FK and field
   loops are re-copied inside `.extend({…})`.
   **Scenario:** the next behaviour column is added to the non-child branch only. A child's own output, and with it
   its flat output and the base's `OfKind` union, silently lacks the column, and tsc stays green.
   **Fix:** render the object once under
   `const _schema = familyChild ? classNames.ownOutputSchema : classNames.outputSchema`, then append the child's flat
   `extend` after it. Do the same for the create DTO's field lines.

4. `templates/_shared/inheritance.mjs:348-351,384-385`. **The DTO schema-naming rule has a second copy.**
   `familyReads` builds `Create${baseClass}Schema`, `${baseClass}OutputSchema` and
   `${entityClassName(c.name)}OwnOutputSchema`, plus the `dto/create-…` and `…-output` stems. Those names already have
   an owner: `entity-locals.js:2618-2624` (`createSchema`, `outputSchema`, `ownOutputSchema`) and `outputPaths`.
   **Scenario:** #894 moves the generated names into `src/derived/api/names.ts`. Whoever moves the names in
   `entity-locals.js` leaves this cross-module copy behind. Each child's import of its base's schema then breaks. It
   fails loudly at tsc, but the rule has two owners.
   **Fix:** add one `dtoSchemaNames(entity)` helper (and a DTO-stem helper) next to `entityClassName` /
   `repositoryClassName` in `src/derived/api/names.ts`, and have both callers read it.

5. `templates/entity/new/backend/search-controller.ejs.t:25,64`. **A child's search controller declares the child's
   own row type, not the flat one.** This template was not updated in S5. The generated
   `meeting-search.controller.ts` returns `Promise<Page<Meeting>>`, the child's columns only, while
   `SearchMeetingsUseCase.execute` returns `Page<MeetingFlat>` (`search.ejs.t` was updated). It compiles because the
   flat row is assignable to the narrower type.
   **Scenario:** code typed against the controller loses `kind`, `occurredAt`, `source` and the other base columns that
   the body actually carries.
   **Fix:** for a child, print `<Entity>Flat` from the repository, as every other child-reading template in this PR
   now does.

6. `templates/entity/new/backend/use-cases/list.ejs.t:149-155`. **`sort_by=id` with a filter is refused.**
   `isBaseColumn` is tested first, and `id` is a column of both tables (the child's key is the base's key).
   **Scenario:** `GET /meetings/search?search=q&sort_by=id` is a 400 that calls `id` "a column of communication",
   although the child-rooted path can sort on the child's own `id`. The same happens for any column both tables carry,
   such as the tenant column.
   **Fix:** on the child-rooted path, check `hasColumn(<child>, col)` first, and refuse only a column the child table
   lacks.
