# @pattern-stack/jobs contract

> Describes the current contract. Code and tests are authoritative; update this doc in the same change.

> **In codegen (JOBS-3).** The host is a codegen-generated app: the job tables are this package's own
> (`@pattern-stack/jobs/postgres`, `src/postgres/tables.ts`), re-exported by the app's schema barrel; jobs are `defineJob`
> / `jobFactory` exports under `<backend_src>/jobs/`, listed in the generated `<generated>/jobs.ts`; the host module is
> codegen's `JobsEngineModule` (`runtime/subsystems/jobs/`), or under pattern-stack wiring the `jobs` system. Tenants are
> any tenant id, and `SYSTEM_TENANT` is a single-tenant app's. Codegen's spec is `docs/specs/JOBS-3.md`.

`packages/jobs`: the shared job module (`@pattern-stack/jobs`), framework-free (its only dependency is `zod`; `src/__tests__/fences.test.ts` blocks Nest, Drizzle, BullMQ and workspace-package imports, subpaths included) — a **job** is code (`defineJob`, its steps added in order, each reading the earlier outputs by name, typed), a **run** one durable execution, a **step** one recorded stage, an **item** one keyed piece of a `mapStep`; the deterministic step engine and `processChunk` (claims fenced, transient retries on Temporal's `RetryPolicy` shape, a deterministic failure split to the bad item, `stopWhen` read over the settled prefix with speculation recorded, a spent budget pausing; spend recorded unfenced, so a call that lands after a cancel or a lost claim keeps its cost (`withSpend` for a call that paid and threw, `BatchResult.failed` to fail items without throwing); a cancel aborts in-flight calls through `ctx.signal` while a pause lets them finish; a step parks its run, `waiting`, on a gate (`gate`, `waitFor`, `GateClosedError`) held on its step's row, woken by the sweep's due read or `openGate`, never failed or skipped; or on a signal, a step that waits for a person (`waitFor({ signal, value, accept?, authority?, timeout? })`), settled by `signalRun` (the value parsed and accepted, the first signal wins, it is the step's output) or its timeout; and a step reads another completed run's output, typed, through `ctx.outputOf(job, runId)`, which `admit` has too, each refusal an `InputRefusedError`; a step starts child runs and waits for them (`children`, `child`: one slot per key for good, an even share of the parent's remaining budget unless a slot carries its own, a cancel or pause cascading down the tree, `retryChild`/`skipChild`, `treeSpend`, at most 3 deep)), where values live (a run's input, a step's output and a map step's results kept by the store as plain JSON beside the run's bookkeeping, at most 1 MB each and refused when not plain JSON, unless the definition names a recorder for domain data; no job gets tables of its own, so a new job needs no migration), the ports (store, executor, limiters, event sink, step and result recorders, clock), a step's limiters (`'llm-calls'`, `{ name: 'decisions', per: 'tenant' }` for one bucket per tenant, or a list; taken sorted by name, a plain step holding its slots for its run; like gates, never in the definition version), the in-process adapters (`localLimiters` in memory, per process), the Postgres store (`./postgres`, over the `job_*` tables `./postgres` declares) and the BullMQ executor (`./bullmq`), each with its framework an optional peer, the Redis limiters (`./redis`: `redisLimiters`, one quota across processes on a structural client, no dependency), the Nest layer (`./nest`: one `JobsService` over the `JobActor` union (member, admin, API key, operator, system) and every access rule, the input-ref registry the app's contexts register into, and the sinks, the active span written through `@opentelemetry/api`; the app's host module (codegen's `JobsEngineModule`) binds its tokens), and in `./testing` the `storeContract` every store passes, the `limiterContract` every limiters adapter passes, and the `replayContract` (the Temporal-ready rules as a test) every job passes. See [`packages/jobs/AGENTS.md`](packages/jobs/AGENTS.md). The app's jobs live under `<backend_src>/jobs/`, where a job step is a surface over an application capability.

## The four concepts

- **Job**: the definition of an operation, in code, registered once per process: a key, a typed input and output (zod), and its steps in order. A job states facts about its work (a map step's `batch: { max }`, its `limiter`, its `key`, `stopWhen`, `retry`), never chunk sizes, parallelism, workers, queues or claims. It also declares who may reach it (`define/facts.ts`): its `audience` (`'internal'` by default, or `'public'`), its `authority` (the level that reads its runs, starts a dry run and starts a real one: `member` < `tenant-wide` < `admin`), its `limits` (the most one run may use), an optional `admit` check of a parsed input, and an optional `subject`: what a run is about, named from its parsed input (`(input) => ({ kind: 'document', id: input.documentId })`), a free-text kind (≤ 64) and id (≤ 255) with no registry of kinds (provisional), computed by `startRun` after the request's fields and stored on the run (`Run.subject`, `job_runs.subject_kind` / `subject_id`, both null or both set), so a caller never names it and a bad one is the definition's `JobDefinitionError`. The app's service applies the levels and limits; `startRun` runs `admit`.
- **Run**: one execution of a job, durable: the request (job key, input, tenant, trigger, requested by, budget, dedupe key) and the record (status, steps, spend, error, the definition's `jobVersion`). `pending → running → completed | failed | canceled`, with `paused` beside `running` (a spent budget or an operator; resume continues it) and `waiting` beside it too (its step parked on something outside the run, see Waits and gates; it moves by itself when its wait settles).
- **Step**: one stage of a run. Steps run in the order the job lists them; each one's output is recorded before the next starts, and a resumed run reads it instead of running the step again. A plain `step` runs once; a `mapStep` runs one function over many items. A plain step may declare how it reads on a run page, `present` (`define/item-view.ts`: a `StepPresenter` from `{ output, status, error }` to a `StepView` `{ label?, summary, detail? }`, checked against `stepViewSchema`, or null): the same rules as an item's, below; with none, a throw, null or a refused answer, a reader shows no summary and the stored output still.
- **Item**: one independent piece of a map step: a ref (an entity id, never content) and its idempotency key. Its result is stored once per key within a tenant and the step's scope (`<jobKey>/<step>`, or the `cacheScope` it names, which every step naming it shares: a name without `/`, for a step the store keeps, and every step sharing it declares the same `result` schema object, checked by `defineJob` and `createRegistry`); the first write wins. A map step may declare how each item reads on a run page, `present` (`define/item-view.ts`: an `ItemPresenter` from `{ ref, key, status, result, error }`, the result parsed by the step's result schema, to an `ItemView` `{ label, summary?, detail?: [{ heading, text?, quote? }] }`, checked against `itemViewSchema`): pure and synchronous, with no ctx and no I/O, so what the label needs is stored in the result; run at read time and never stored, so changing it changes what past runs show; never in the definition version; with none, a throw or a refused answer, a reader falls back to the item's key.

Chunks, claims, the executor and the limiter are the engine's: a job author never sees them. Export paths are cut by audience: `@pattern-stack/jobs` (authors and callers), `@pattern-stack/jobs/ports` (adapter authors; `processChunk` is the one function every executor calls per chunk), `@pattern-stack/jobs/testing` (tests, evals and scripts, never production code: `MemoryJobStore`, the memory recorders, `storeContract`, `limiterContract`, `replayContract`, fakes, toy jobs), `@pattern-stack/jobs/redis` (`redisLimiters`), `@pattern-stack/jobs/nest` (a Nest host: the app's surfaces and its host module). The `exports` map blocks deep imports; the engine's internals are not exported.

## Waits and gates

A step can park its run on something outside it. The run is then `waiting`: nothing of it is in flight, it holds its dedupe key (`waiting` is in `ACTIVE_RUN`), and it is not open work (`openRunIds` stays pending and running). Gates, signals and child runs (`children`) park on it.

- **The wait lives on the step's row** (`StepState.wait`: its kind, its name, `since`, and `wakeAt`, when the advance looks again), never in the executor. `JobStore.park` and `unpark` move the step and its run through a CAS (park only while the run is running or waiting and the step not settled; a step that parks before it ran gets a row with no attempt spent; a paused or ended run parks nothing). Kind and name stay after the wait settles, as what it waited for.
- **A wake is only a submit.** An executor wakes a run by submitting it, and the run's next advance reads the step's row and decides: before `wakeAt` it rests (a run resumed from a pause parks again with the same wake); once due, it reads the gates again. The sweep wakes due waits (`store.dueRunIds(now, limit, after?)`, keyset like `openRunIds`, through a partial index on `wake_at`): the in-process executor's drive loop beside `sweepExpired`, BullMQ's `sweep()`. It never changes a parked run's status.
- **A gate** (`gate({ name, isOpen(ctx), poll?, maxWaitMs? })`) is a named condition outside the run, declared once and shared by the jobs that read it; `isOpen` reads the step's context, so it can be about the tenant or the run's own input. A step names its gates (`step({ gates })`, `mapStep({ gates })`); `waitFor({ gate })` is the step that only waits (no work, a void output). The engine reads a step's gates before the step runs (a plain step each time it is about to run, a map step before it starts) and at the start of each chunk, before `hydrate`. A closed one parks the step (`step.waiting`), its first poll `poll.initialMs` (default 1 min) from now, then as long as it has waited so far, up to `poll.maxMs` (default 15 min); past `maxWaitMs` the step fails (`GateTimedOutError`). A batch that finds its gate closed partway throws `GateClosedError(name)`: its items stay pending, no attempt is spent (a plain step's attempt is given back), its spend (`withSpend`) is recorded, the chunk's other calls finish and write, the chunk yields and the step parks. A closed gate is never a failure or a skip. `GateClosedError` for a gate the step doesn't declare is a definition error. A gate's name is a code constant (it reaches rows, events and logs).
- **A push** (`openGate({ store, executor }, tenantId, name)`) makes every step of that tenant waiting on that gate due now (`store.wakeGate`) and submits their runs; polling stays the backstop for a push never sent, and a failed submit is picked up by the next sweep.
- Gates and limiters are not part of a definition's version: they change when work runs, never what it computes.
- **A signal** (`waitFor({ signal, value, description?, accept?, authority?, timeout? })`) is a step that waits for a person: kind `wait`, no work of its own, never gated or limited. The advance parks it (`step.waiting`, wait kind `signal`, its `wakeAt` the timeout or none) and `signalRun(deps, { runId, step, signal, value, by })` settles it: the value is parsed by the step's schema (`SignalRefusedError` `signal_value_invalid`, each issue's path and code, never the value), checked by `accept` (`InputRefusedError`, its own code, as `admit`), checked storable, then written in one CAS (`store.settleWait`: the step `waiting` for that signal; its value recorded as the step's output, kept by the store, so a store that keeps no values refuses the job; the step completed with `settledBy`; a waiting run back to running, a paused one left paused for its resume). The first signal wins; one that finds the step not waiting for it is `wait_not_open`, and an early signal is never buffered. It emits `step.signaled` (`byTimeout`) and submits the run. Who may send it is `signalAuthorityOf` (its own `authority`, else `authority.start`, or `authority.dryRun` for a dry run); the surface applies it to its caller. A timeout (`{ afterMs, fallback }`; `fallback`, not `then`, because a `then` key makes an object thenable) is met by the advance once due: `'fail'` fails the step (`WaitTimedOutError`), `{ value }` settles it as no one's signal. Its signal name, value schema and timeout are in the definition version; its authority is not. `runToCompletion` takes scripted signals (`signals`), and returns a run waiting on a signal nothing will send.

## Child runs

A step can start runs of other jobs and wait for them (`children({ job, each, onFailure })`, or `child({ job, input })` for one, whose output is the child's own). The child job must be in the same registry.

- **The slot is the dedupe.** A children step's slots are its items (`item_key` the child key, `item_ref` the child run id, no chunk), so a key has one slot for good. `store.startChildren` starts a step's children in one transaction under the parent's lock: the step's row (kind `children`), a slot per new key, and a pending child run for each slot it inserted, so a step run again (after a crash, or by a second advancer) starts nothing new. Only an operator's retry puts a second run in a slot (`retryChild`: a failed slot only, one more attempt, the failed attempt's budget unless another is given); a skip settles a failed slot (`skipChild`; a `child` step has none). A child takes no dedupe key of its own.
- **What a child inherits:** its parent's tenant (a composite FK makes another impossible), `dryRun`, requester, trigger and cache mode, and the deadline and `maxItems`; its own job's current version; the engine's chunk defaults. Its budget is its slot's own (`ChildSpec.budget`, d19), else an even share of what the parent has left (`maxUsd`, `maxCalls` over the slots with none, read from `treeSpend`), so the tree stays inside the parent's cap. Runs nest at most `MAX_DEPTH` (3) deep and a step starts at most `MAX_CHILDREN` (100).
- **Waiting:** the step parks (wait kind `children`, the child job's key) and then reads its slots once more, so a child that ended before the park is seen and one that ends after it pokes the step: a child's terminal transition sets its parent's waiting step's `wakeAt` to now, in the same transaction, the parent's row locked first, and the engine submits the parent (`AdvanceDeps.submit`, the fast path; the sweep's due read is the durable one). The advance settles slots (`settleSlots`: done, or failed with the child's error type or `Canceled`; `child.started` and `child.ended` events) and decides by `onFailure`: `hold` (default) waits for a retry or skip; `continue` completes with the failure in the output; `fail` fails the step once every slot settled. The output (`ChildResults`: results, failed, skipped) is read back from the slots and the children's outputs, never stored twice.
- **Down the tree:** a terminal transition cancels every open descendant in the same transaction; a pause pauses them with reason `parent`, and a resume resumes only those (`transition` returns them as `cascaded`). A child never moves its parent's status. Each run's spend is its own; `store.treeSpend` sums the tree, every attempt once.
- **The registry checks parents:** every child job registered, a parent internal, a parent's read, dry-run and start levels each at least its children's, no cycle, no path longer than `MAX_DEPTH`. A children step's version hashes the child's key, input and output shapes, `onFailure` and whether it is one child; never the child's own version.

## Reading another run's output

`ctx.outputOf(job, runId)` (and the same reader on `admit`'s request, so a start refuses a bad reference before any run exists) reads a completed run's output, typed by its job, from the store and the registry, so a step never holds the store. `outputOf` is a reserved step name. Each check throws `InputRefusedError` (non-retryable, naming only the caller's own ids), in order: `run_not_found` (no such run, or another tenant's: never told apart), `run_wrong_job`, `run_not_completed` (pending, running, waiting, paused, failed and canceled alike), `run_output_unreadable` (its output no longer parses with `job.output`). It only reads a terminal run's output, written once, so a step that reads it stays a function of its records on every executor.

## Limiters

A limiter is a shared quota a step names; the engine takes it, a job author never does (t11).

- **A step names its limiters** (`define/limits.ts`): `'llm-calls'` (one bucket for every run), `{ name: 'decisions', per: 'tenant' }` (one bucket per tenant, key `decisions:<tenantId>`, from the run, so deterministic), or a list. A map step names at least one, and each call takes every one; a plain step may name some (`step({ limiter })`) and holds a slot on each for its whole `run`, released however the attempt ends (a `ThrottledError` it throws throttles them). **A throttle is never a failed attempt** (`throttleOf`: a `ThrottledError`, or a provider error with `status`/`statusCode` 429): the permit is released throttled, the limiter waits out Retry-After (a plain step with no limiter sleeps it, default 1 s), and the same batch or the same `run` is asked again in the same attempt, so a run of 429s never exhausts `maximumAttempts`; a cancel's abort ends the wait. The engine takes a step's limiters sorted by name (`stepLimitersOf`), so two calls never wait on each other's slots; a name twice in one step is a definition error. The call takes its slots before it reserves budget (`acquireAll` in `engine/limits.ts`), and a 429 on release throttles every bucket the call drew on.
- **The port is `Limiters`** (`get(name, key)`): the name finds the config (`LimiterConfig`: `inFlight`, optional calls and tokens per minute, `leaseMs`), the key the bucket. Executors take `limiters: Limiters`, default `localLimiters()`.
- **`localLimiters(config, { fallback?, clock? })`** (core): one in-memory `localLimiter` per key, for in-process runs, tests and scripts; a name the config doesn't list takes `fallback` or `DEFAULT_LIMITER`. N processes get N times each quota.
- **`redisLimiters(client, config, options)`** (`@pattern-stack/jobs/redis`, no dependency: `client` is the structural `RedisScripting`, one `eval(script, keys, args)`; `evalScripting(client)` adapts an ioredis-shaped `eval(script, numKeys, ...keysAndArgs)` to it): one quota across every process. Per key, a Lua script drops expired leases and window entries and takes a slot only under the cap and inside the per-minute window; leases are a sorted set scored by expiry, so a crashed holder's slot frees itself after `leaseMs` (`DEFAULT_LEASE_MS`, 5 min, outliving the longest call) and a late release frees nothing more; a 429 sets a shared `blocked` until its Retry-After, so every holder backs off, while halving the cap stays each process's own. A wait polls with jitter (50–250 ms); a release that cannot reach Redis leaves its lease to expire.
- **`limiterContract`** (`@pattern-stack/jobs/testing`) holds every adapter to the same rules, holder to holder: the in-flight cap, the per-minute window, a 429 blocking every holder, an expired lease freeing its slot, one bucket per key, and an aborted wait taking nothing. The local adapter runs it in this package; the Redis adapter runs it on Valkey in the app's e2e.

## Layers

- `model/` imports only `model/`; `ports/` and `policy/` import only `model/`; `define/` imports `model/`, `policy/` and the port types (the recorders) it names; `engine/` imports `model/`, `define/`, `ports/` and `policy/`, never `adapters/`.
- Two run rules shared by every store sit in `model/run.ts` beside the types they read: `canTransition` and `budgetStop`. Every other rule is in `policy/`.
- Executors drive the engine: an executor adapter (`adapters/in-process-executor.ts`, `src/bullmq/`) may import the engine's entry points: `engine/advance-run.ts` and `engine/process-chunk.ts`, the emitter (`engine/emitter.ts`), the submit checks in `engine/values.ts` (`assertStoreHoldsValues`, `assertStoreSafeFor`), the heartbeat's rule (`engine/heartbeat.ts`), the stop scans (`engine/stop-scan.ts`), the deps types (`engine/deps.ts`), and, for `runToCompletion`, `engine/start-run.ts`, `engine/context.ts` and `engine/signals.ts` (its scripted signals). It never imports a step's internals (`run-step.ts`, `run-map-step.ts`, `batches.ts`). The Postgres store imports `model/` and `ports/` only. Every module beside an executor is part of it; `src/__tests__/layers.test.ts` holds this list, the layers above and the engine's determinism.
- An executor guarantees at most one advancer per run at a time.
- The engine's one diagnostic is the emitter's default `onSinkError`, a line on stderr naming the event and the error's type; an executor may supply its own.

## Where values live

A job has three kinds of value: the run's **input**, each plain step's **output**, and each map step's **item results**. Each lives in the store, as plain JSON kept beside the run's bookkeeping, unless its definition names a recorder. A new job therefore needs no table of its own and no migration; product data that other surfaces read belongs in its domain's tables, written by the step like any other domain write, never in a table per job.

- `defineJob({ inputRecorder })` and `step({ recorder })` take a `StepRecorder<T>` (`save(runId, value)`, `load(runId)`); `mapStep({ results })` takes a `ResultRecorder<R>` (`save(tenantId, runId, results)`, the first write per tenant and key winning; `load(tenantId, keys)`). A recorder is the exception, for a value that is itself domain data (it writes to that domain's tables); it is never a table made for one job.
- Without a recorder, the store keeps the value (`keepsValues: true`: the memory store, and Postgres from `@pattern-stack/jobs/postgres`). A stored value must be plain JSON and at most `MAX_STORED_VALUE_BYTES` (1 MB) as JSON: no `Date`, `Map`, `Set`, `bigint`, class instance, `NaN` or `undefined` in an array. The engine refuses any other with `JobDefinitionError` before it is written, on every store (an input when the run is started, a step's output by failing the run, an item's result by failing the item), except a run input over the size, which is the request's to fix and refused as `RunPlanningError` (every surface answers it as a refused input, 400 `input_invalid`), so a value never comes back changed (a `Date` from a JSON column is a string). Send a time as an ISO string. A store that keeps no values (`new MemoryJobStore({ keepsValues: false })`, for testing recorders) is never handed one: `startRun` and `submit` refuse a job with a value that has no recorder.
- A void value opts out explicitly with `'none'`, which the types allow only for a void input or output (a map step's `'none'` is checked at run time: `R` is inferred from its `run`). A `'none'` value that turns out not to be void is a definition error. Nothing is dropped silently, and void results are never cached across runs.
- The engine reads and writes each value only where it lives (`src/engine/values.ts`). A recorder is written before the store marks the items, so after a crash between the two the next attempt reads the items as cached. Only the request that created a run records its input, so a run whose recorded input is missing (a crash between `createRun` and the save) fails with `RunPlanningError` before any step runs, even after a dedupe hit.

## How to add a job

1. Declare it with `defineJob`. In the app, a job is an export of a file under `<backend_src>/jobs/`, where a job step is a surface over an application capability, in run order. Add steps in order through the chain; each step reads the input and every earlier output by name, typed:

   ```ts
   export const calibration = defineJob({
     key: 'document.reindex',
     input: calibrationInput,
     output: calibrationResult,
     steps: (s) =>
       s
         .add('band', step({ run: ({ input }) => readBand(input), recorder: bandRecorder }))
         .add('judge', mapStep({
           items: ({ band }) => band.observationIds,
           key: (ref, { input }) => `${meaningOf(input)}:${ref}`,
           hydrate: (refs) => loadRows(refs),
           run: (batch) => judgeRows(batch),
           batch: { max: 200 },
           limiter: 'llm-calls',
           stopWhen: twoSlicesUnder(0.5),
         }))
         .add('line', step({ run: ({ judge }) => placeLine(judge) })),
   });
   ```

2. The last step's output is the job's output, validated by `output` when the run completes. Later, bump `version` (an integer, default 1) when a change to a step's code must not reach a run already open.
3. Register it with every other job of the process (`createRegistry`), and run it through an executor (`InProcessExecutor`, or `runToCompletion` for scripts and evals). In a codegen app, export it from a file under `<backend_src>/jobs/`: `codegen entity new` lists it in `<generated>/jobs.ts`, which the host binds as `JOBS_DEFINITIONS`.
4. Keep every value plain JSON and small (see Where values live): ids, strings, numbers, times as ISO strings. A value that is domain data goes to its domain's tables; nothing gets a table of its own.
5. When an input field names a domain id the operator should pick by name (an indicator, play or Signal version), mark it with zod metadata: `z.uuid().meta({ ref: 'document' })`, which the app's jobs write as `jobRef('document')` (`@pattern-stack/jobs/shapes`, typed by `JOB_REF_KINDS`). It is plain zod, so the core imports nothing for it; `./nest` reads it from the input's JSON Schema (`refFieldsOf`): Start run looks the id up by name, and every actor start resolves it in the run's tenant (400 `ref_not_found` otherwise). A kind a registered job names must have a `JobInputRefSource` registered by the module of the context that owns it, or the boot fails.
6. Add it to `replayContract` in its tests: it must pass the same determinism check as the engine.
7. Decide who reaches it. Leave it internal unless a caller-facing surface needs it. A public job declares `limits` (each a positive finite number; `maxItems`, `maxCalls` and `maxDurationMs` whole numbers), and its `authority` holds `read` ≤ `dryRun` ≤ `start`. A job with a `side-effect` step needs `admin` to start a real run; its dry run may sit at a lower level (calibration's is `tenant-wide`), so every side-effecting step must publish nothing under `ctx.dryRun`. Give it an `admit` when an input can be well formed and still wrong for the tenant (an id it doesn't hold): it throws `InputRefusedError(code, message)`, whose code is a bounded identifier and whose message names nothing outside the job. A public job's input and output must be camelCase zod objects, or the app's boot fails.

## Temporal-ready rules (review rules)

A Temporal (or Restate, Hatchet) executor must be able to replace the in-process and BullMQ ones without touching a job, the run tables or the API. Review every change to `src/engine/`, `src/define/` and every job against these:

- **The engine's control flow is deterministic.** Deciding the next step, planning chunks and reading the stop rule read the clock, randomness and I/O only through the ports (`Clock`, `JobStore`, `EventSink`, `Limiter`, `StepRecorder`, `ResultRecorder`). No `Date.now()`, `new Date()`, `Math.random()`, `setTimeout` or `fetch` in `src/engine/`.
- **Side effects happen only inside steps and item batches**, each recorded or safe to repeat. Execution is at least once: a step whose worker dies after its effect and before its record runs again, on every executor (Temporal's activities included). A step that changes the world declares `effect: 'side-effect'` and makes that effect idempotent itself, keyed by `ctx.runId` and the step (an upsert, a provider's idempotency key, or a check of what it already wrote); the flag does not make it exactly once. `startRun` refuses such a step on a store that can lose writes, before the run is created.
- **A step returns a small value or a reference.** A stored value is capped at 1 MB of JSON (Temporal caps a payload at about 2 MB); bulk data goes where it belongs (a domain's tables, or object storage) and the step returns its id or key. A map step's output is read back from its item results, never stored again.
- **Item state lives in our store, never the executor's.** A chunk is the unit of dispatch; items, results and counts are the store's.
- **Claims, heartbeats and retries belong to the executor adapter.** The engine says only what may be retried (`RetryPolicy`, Temporal's shape; `NonRetryableError`) and fences every chunk write by its claim's token (`ClaimLostError`): one worker swept and re-claiming its own chunk holds a new claim, and the stale one is fenced out.
- **Ids come from the store, never the engine.**
- **A paused run waits for a resume; budget checks sit between steps and chunks** (a spent budget pauses, never fails). A plain step re-reads its run before every attempt, so a cancel or a pause stops its retries. A pause lets a map step's calls in flight finish and write (below); only a cancel, a failure or a lost claim aborts them. A call reserves its estimated cost once it holds its limiter slot, and the reservation is settled by that estimate: released by the call's write, returned when the call fails, dropped when its chunk settles or is swept.
- **The result never depends on how far ahead the engine worked.** A map step's `stopWhen` is read only over the contiguous settled prefix, and items past the stop are discarded; `speculated`, `used` and `overshoot` record the width, not the answer. A chunk reads the stop after each batch lands (`stopFound`), holding the batch's limiter slot until it has written and read the stop, so once it trips no batch is issued (one waiting for its slot gives it back) and only what was in flight overshoots, at most the limiter's width; the chunk then settles completed and the stop skips what it left. A stop also ends planning: `stopStep` marks the step planned, so a page planned after it adds nothing and the planner stops paging its source. The stop is read incrementally (`engine/stop-scan.ts`): each executor keeps a `StopScans` (`EngineDeps.stops`), one scan per step holding the settled prefix read so far (settled items never change), and `readStop` reads on from it with `store.items(runId, step, { from, limit })`, a window of 8 doubling to 256 while all of it is settled; so a read costs what settled since plus a few rows, never the step. A process without a scan (a crash, a dropped one, past 256 kept) starts again from the first item.
- **A wait is durable state in the store** (the step's row), never in the executor: an executor only submits, and the advance decides. `replayContract` closes a gate at chosen calls and asks for the same result, with no key asked twice and nothing failed or retried for it; for a job with a wait step it sends the subject's scripted signals (`signals`, by step) in every run, and delivers each with the process dying before the advance, asking for the same result and refusing a second delivery.

`runToCompletion` registers a job's descendants with it, so evals and the contracts run a parent whole. `replayContract` (`@pattern-stack/jobs/testing`) checks what a test can observe of these, with each run under its own tenant so no run is answered from another's results: a job run under different chunk sizes, widths and call orders gives one result; no key is answered twice in one process; a run stopped at any call and resumed from its records gives the same result without asking again for a recorded item or running a completed step; a map step with items is really asked; a gate closing at any call parks the run, which carries on to the same result; a signal delivered before a crash resumes to the same result and counts once; and every timestamp, event time and a deadline are read on the clock it was given. It can't see every breach (a rule broken only on a path the job never takes, or a wall-clock read that happens to agree), so review still applies the rules.

## Other review rules

- **A batch passes `ctx.signal` to every provider call.** A cancel, a failure or a lost claim aborts the calls in flight through it at the chunk's next heartbeat (one beat, a third of the claim TTL; `abortsInFlight`, one rule for every executor). A pause does not: `reserve` refuses new calls at once, the calls in flight keep their claim, land and write, and the chunk then yields. A call that can't take the signal runs to the end after a cancel, and is covered by the next rule.
- **A run's cache mode** (`Run.cache`, stored as `cache_mode`) is decided once, at `startRun`: the request's `cache`, else the job's `cacheFor(input)`, else `read-write`. A `read-write` run reuses a stored answer for its key and stores new ones (first write wins). A `refresh` run reads no cached answer, re-asks every item and overwrites the stored answer with its own, inside the fence (while its claim holds; on Postgres an `UPDATE` in the fenced transaction after the unfenced insert), so its output is what it paid for; a refresh's late answer (a lost claim, an ended run) lands only where no answer is stored, like any late answer. A step with a recorder keeps its own rules. `cacheFor` is a fact like `admit`, not in the definition version: the mode is stored on the run, so an open run resumes under the mode it started with.
- **Spend is never fenced.** `writeResults` writes three parts: the results (unfenced, first write wins, a refresh's overwrite fenced), the spend (unfenced, on the run and the chunk) and the marks, counts and reservation release (fenced by the claim). So a call that settles after a cancel or a lost claim records what it cost, its items keep their status, and its results stay in the cache (valid for their keys, and paid for). A canceled run's cost can rise for one call's duration after the cancel; its counts never move once it ends. A call that paid and then threw says so with `throw withSpend(err, spend)`, which keeps the error's identity and retry class, and the engine records it with `store.addSpend`. A batch that fails items without throwing returns `BatchResult.failed` (`{ index, errorType }`, each index once, the type a bounded identifier): they fail alone, never retried, and the call's spend and the other results are kept. Each call's spend is recorded exactly once, by its write or by `addSpend`.
- A deterministic failure fails its item alone: a `NonRetryableError` from a batch splits it down to the bad item, and an answer the step's `result` schema refuses fails as `ResultSchemaError`, whatever the chunk size. A failure in `hydrate` or a batch of the wrong length is a definition error and fails the chunk's pending items.
- Events come from the fixed list (`JOB_EVENT_TYPES`) and carry ids and counts, never content: no item text, prompts, inputs or outputs, and an error only by its type.
- Results, the cache and dedupe are scoped by tenant: a result is keyed by tenant, scope and key, and a dedupe key holds at most one open run per tenant, job, and dry or real (a real start is never answered by an open dry run, nor the reverse). Never widen either across tenants.
- A run is read against the definition it ran: an open run made by another `definitionVersion` is refused (`RunVersionConflictError`, a `JobDefinitionError`), never resumed under new code. The version is structural: it hashes the job's key, its `version`, its shapes and each step's declared facts (a map step's batch size, result schema, `cacheScope` only when set, and, only when declared, `stopWhen: true`; its `key` function and its stop's rule are code and add nothing, and its `present` is presentation and adds nothing), never code text (a script's TypeScript and a worker's compiled dist differ in text, and a hash of it would strand every run started by another build). Bump `defineJob({ version })` when a step's behaviour changes in a way an open run must not resume under. **A bump drains, then fails** the old version's open runs: until a process has been up `versionGraceMs` (BullMQ `VERSION_GRACE_MS`, 15 min, past a rolling deploy; in-process 0, one process having no other to leave them to), a run of a version it doesn't have is left to a process still on it; after, its next advance fails it with `JobVersionGoneError` (`AdvanceDeps.versionGone`), never leaving it open. Its chunks are never worked under another version. A run of a job key the process doesn't register is still only left alone. Paused runs stay paused until resumed. A part of a shape JSON Schema can't express (a date, a custom check) hashes as `{}` in place, so a change inside it also needs a bump.
- A job's facts (`audience`, `authority`, `limits`, `admit`, `subject`, `cacheFor`) are not part of its `definitionVersion` (a subject is computed once, at start, and only labels the run): who may start a job doesn't change how a run runs, so changing them strands no open run.
- A public job declares `limits`; `defineJob` refuses one without. A job with a `side-effect` step needs `start: 'admin'` (`defineJob` refuses less), while its `dryRun` may be lower. So **a side-effect step honours `ctx.dryRun`: it publishes nothing on a dry run** (a tenant key may start dry runs, and a key writes nothing), and the job's tests run it dry and assert no side-effect write. The engine can't see this one, so review holds it.
- `admit` runs inside `startRun`, after the input parses and before the run is created, for every caller: a refusal creates nothing and holds no dedupe key. `startRun` answers `{ run, created }`.
- Every store adapter runs `storeContract` (its harness names two tenants the store can hold runs for); every behavioural change to the store port updates the contract in the same change. A store that keeps no values passes the same suite: its value cases assert the refusal instead, and its recorder-backed cases run, resume and cache like any store's.
- The single-run reads (`getRun`, `progress`, `stepStates`, `chunks`) are not tenant-scoped: a surface must check `run.tenantId` before returning anything. `getRun`, `progress`, `transition` and `runInput` of an unknown id throw `RunNotFoundError` in every store (a store-contract case; on Postgres every path that reads or locks a run row), so a surface tells not found from a database error by type, never by message. `listRuns` is, and is paged (`limit`, `before`), filtered by job, status and subject (`Run.subject`, kind and id both equal).
- A step starts as a CAS on its attempts (`startStep(runId, step, { attempts })`): it starts only while the step is at the attempts the caller read (0 before its first start) and isn't completed, skipped or failed, else it changes nothing and returns null. Of two advancers racing on one attempt only one runs it (the other leaves the step: a plain step's `left`, a map step to its chunks), and an ended step is never restarted.
- A per-chunk dispatcher claims by name (`claimChunk(owner, ttlMs, ref)`), which never falls back to another chunk; `pendingChunks(runId, limit)` (due first: `runAt`, step, chunk) serves the dispatcher, a window at a time; `chunks(runId)` reads them all, and `openRunIds(limit, after?)` (a keyset in its own order) serves the sweeper's backstop.
- A map step's `key` depends only on what the work means and which item it is about, never on the run, the time or the attempt. Keys reach events (`item.failed`) and logs, so a key never embeds content: name the meaning by a version or a hash, and the item by its id. An item key names everything its result depends on: the inputs, the definition or standard version, and the tenant's config hash. A key that leaves one out serves a stale answer: the result cache is shared by every run of the step's scope (`<jobKey>/<step>`, or its `cacheScope`) within the tenant, so the second run of a key that missed a meaning is a silent no-op (no calls, no cost) that reports the first run's answers as its own. To ask again under the same key, run with `cache: 'refresh'` (or have the job choose it, `cacheFor`).

## The Nest layer (`./nest`)

`@pattern-stack/jobs/nest` is the jobs capability in a Nest host, the way `@pattern-stack/query-surface/nest` is. It ships no controller: every surface is the host's.

- **One `JobsService`, three views, chosen by the actor** (`nest/jobs.service.ts`; every method takes the part of the `JobActor` union its view serves, and the view decides the wire shape):
  - the **public view** (tenant actors, `@pattern-stack/jobs/shapes` shapes): `listJobs`, `loadJob`, `start`, `listRuns`, `loadRun`, `loadRunChange`, `cancel`;
  - the **operator view** (the superuser, `@pattern-stack/jobs/shapes` shapes): `listJobsWithHealth`, `listRunsAcrossTenants`, `listRecentRuns`, `loadRunRecord`, `listRunItems`, `loadStepOutput`, `listRunEvents`, `listEvents`, `listRefOptions`, `startForTenant`, `signal`, `retryChild`, `skipChild`, `controlRun`;
  - the **system view** (the app acting for one tenant): `startSystemRun`, `openGate`, `loadSystemRun`.
  The engine's start refusals are mapped once (`startRefusalOf`), each view keeping its wire (`version_conflict` on REST, `run_version_conflict` on `jobsOps`; an admit refusal 422 on REST, 400 on `jobsOps`; the system view rethrows them as they are). One run read (`runOf`, 404 `run_not_found`), one budget rule (`budgetFor`: an omitted field is the job's limit, the public view caps each at it, a job with no limits needs `maxItems`), one output read (`storedOutput`: `{ readable: false }` when the job is gone or its output no longer parses, logged), one submit (a failure is logged and the sweep resubmits; no start throws for it).
- **The actor and the policy** (`nest/job-actor.ts`, `nest/jobs.policy.ts`): `member`, `admin` and `apiKey` (tenant actors; the level is the kind's, `TENANT_ACTOR_LEVEL`: member < tenant-wide < admin), `operator` (every tenant and registered job, every level) and `system` (its own tenant's registered jobs, internal ones too, with no job authority, audience or limit ceiling; the job's `admit` still runs). Tenant actors reach public jobs only, in their own tenant: 403 below a visible job's level, and an internal or unknown job, another tenant's run or one below the read level is the same 404. A run's tenant is always its row's. A method's actor type refuses a wrong kind at compile time and its runtime guard throws a plain `Error` for a cast. The operator and the system are capabilities the package trusts: the host builds them server-side only, behind its own gates.
- **Input refs** (`nest/job-input-refs.ts`, d88): the `JobInputRefSource` port (`listOptions`, `resolve`), `JobInputRefRegistry` (`JOBS_INPUT_REFS`, no dependencies, a second source for a kind throws), `matchingRefOptions` and `refFieldsOf`. Each host context registers its own source from its module's constructor; `JobEngineLifecycle.onApplicationBootstrap` checks every kind a registered job names has one.
- **Item views**: `listRunItems` runs each map step's `present` at read time over the stored result (parsed by the step's result schema) and answers `{ …, error, result, view }`; no presenter, a throw or an answer `itemViewSchema` refuses is `view: null`, warned once per step per read.
- **Step views**: `loadRunRecord` gives each completed plain step its `summary`, its step's `present` run at read time over its stored output (only the line, never the output); `loadStepOutput(operator, runId, step)` answers an expanded plain step `{ view, output, error }`, the presenter run over the output (null until the step completed) with its status and error. No presenter, a throw, a null answer or one `stepViewSchema` refuses is no summary and `view: null`, warned once per step per read; the output is answered still. A step the job doesn't define is 404 `step_not_found`, a step of another kind 400 `not_a_plain_step`.
- **Events and tracing** (`nest/event-sinks.ts`, d89): the package's sinks are `activeSpanSink()` (onto `trace.getActiveSpan()` through `@opentelemetry/api`: `step.completed` counts as `jobs.step.<name>.<count>` attributes, `step.failed` and `run.failed` an ERROR status with the error type; it opens no span, writes no content and never throws), `nestLogSink` and `./postgres`'s `eventLogSink`, then the host's (`JOBS_EVENT_SINKS`, optional, the open port), fanned out (`fanOut`: a sink's throw never stops the others). The run's trace root is the host's: its worker passes it as `handle(job, { trace })`.
- **Tokens and the module** (`nest/tokens.ts`, `nest/jobs.module.ts`): all `Symbol.for`. The host binds `JOBS_DRIZZLE`, `JOBS_TABLES`, `JOBS_REDIS`, `JOBS_QUEUE`, `JOBS_DEFINITIONS`, `JOBS_LIMITER_CONFIG`, `JOBS_TENANTS` and optionally `JOBS_EVENT_SINKS`, in a `@Global()` host module (the package module's injector must see them). The package provides and exports `JobsService`, `JOBS_INPUT_REFS`, `JOBS_STORE` (the worker handler reads a run for its trace root), `JOBS_EXECUTOR` (the worker's handlers), `JOBS_PUBLIC_CATALOG`, `JOBS_EVENTS` and `JOBS_CLOCK`; the registry and the operator reads stay its own. A registered job naming a limiter with no config, or a public job whose shapes can't be published, stops the boot. The executor drains in `beforeApplicationShutdown`, before the host closes its Redis client in `onApplicationShutdown`.
- **Dependencies**: `@nestjs/common` and `@opentelemetry/api` are optional peers (one copy, the host's: a second `@nestjs/common` would make every jobs error a 500 on REST, a second `@opentelemetry/api` would leave `activeSpanSink` writing nowhere), `zod` and `@opentelemetry/api` its dependencies. Every injection inside the package is by token, never by class.
- **Tests**: `src/nest/__tests__/` on `bun test`, the service built directly (`__tests__/service-fixture.ts`); the DI proof is the app's `jobs-module` e2e.

## The framework adapters

Each is its own export path with its framework an optional peer (`drizzle-orm`, `bullmq`), so the core and the agents that import `@pattern-stack/jobs` never load either.

- **`@pattern-stack/jobs/postgres`: `PostgresJobStore(db, tables, { now })`.** Durable, and keeps a job's values (`keepsValues: true`) as JSON beside the bookkeeping, never in it: the run's input and each step's output in `job_run_values` (one row per run and name; the input under `input`, a name no step may take), item results in `job_item_results` (one per tenant, scope and key, the first write winning; they outlive their run, as the cache). A run read never carries a value: `runInput` and `stepOutput` read it, and the run and its input commit in one statement, a step's output and its completion in one transaction. An item's result is written before the fenced transaction that marks it, so a lost claim's results still land (first write wins) while its counts don't. Keys are sent as one JSON parameter, never one bind parameter each. Its tables are declared in `./postgres` (`src/postgres/tables.ts`), re-exported by the host's schema barrel, and handed in; `JobTables` is the structural type the backend binds them with (`satisfies JobTables`), so a column that drifts from what the store reads is a type error, and the package never imports the host's schema. `db` is a structural `JobDatabase` (Drizzle's `execute(query, 'objects')` and `transaction`): a node-postgres database or a transaction. Every statement is a `sql` template over the handed table and column objects, with bound parameters, and every row is narrowed by zod in `postgres/rows.ts` (the one mapping of these tables; timestamps are selected as epoch milliseconds, so no driver's type parser is involved). Rules:
  - Every timestamp it writes comes from its `now`, never SQL `now()`, `sweepExpired()` included. The claim's token is `gen_random_uuid()`: ids come from the store.
  - A claim is a lease on the chunk row: `UPDATE … FROM (SELECT … FOR UPDATE SKIP LOCKED)` in one statement, named (`claimChunk` with a ref, never another chunk) or not. Every chunk write is fenced by the row's owner AND token and an open run (`holds`, the memory store's rule), so a same-owner re-claim after a sweep fences out the stale claim; `reserve` and `releaseReservation` are fenced the same way (a stale claim reserves and returns nothing).
  - A transaction that writes a run's chunks or items locks the run row first (`FOR NO KEY UPDATE`), then the chunk: a cancel and a chunk's write never lock in opposite orders. A transaction that reads the run under that lock (`reserve`, a transition, `planItems`) reads it in a statement after the locking one: the locking statement's chunk sums come from its snapshot, taken before it waited, so a reserve that waited on another would miss that one's reservation. The sweep and the claim are single statements that skip locked rows.
  - What a run has reserved and not spent is held on its chunks (`reserved_usd`, `reserved_calls`), one claim's calls each, and `Run.reservedUsd` is their sum on every read: a settle, a sweep and a cancel drop a chunk's, so a crash can't strand a reservation and there is no second total to drift.
  - Tenant scoping: every row's `tenant_id` is copied from its run inside the statement that writes it; the composite FKs make a cross-tenant child impossible. The operator reads read across tenants, off the port, for a superuser surface only (their types in `postgres/operator-reads.ts`, exported from `./postgres`, with `JobOperatorReads`, the interface `PostgresJobStore` implements): `listRecentAcrossTenants({ jobKeys, limit })`; `listRunsAcrossTenants` (job, tenant and status filters, keyset on `(created_at, id)` newest first); `listNewestRunsPerJob(jobKeys, perJob)` (each job's newest runs through a lateral read per job, never its history, in one statement: the rows only; a job's health is the shared `jobHealthOf` in `@pattern-stack/jobs/shapes`, never SQL); `listRunItems` (a step's items a page at a time, failed first and then the rest, each by ordinal: `items()` reads a whole step and is the engine's, never a surface's); `listRunEvents` and `listEvents` (a run's timeline oldest first; the log newest first, by job, tenant and type). Each has the index its query takes (`src/postgres/tables.ts`). Every read is bounded by its `limit`.
  - The event log: `appendEvent(event)` writes one `events` row (`job_run_events`), its tenant, run and job copied from the run row in the insert (an event of a run that is gone writes nothing), ids, counts and types only, as the event list says. The store never emits: `eventLogSink(store)` (`./postgres`) calls it, beside the other sinks, and keeps every event but `step.progress`.
  - The sweep returns at most 1,000 expired claims a call.
- **`@pattern-stack/jobs/bullmq`: `BullmqExecutor(queue, store, registry, options)`.** The store is the truth; BullMQ only dispatches, on one queue with two job names (`JOB_ENGINE_JOBS`): `advance` (one run's step loop, then a dispatch of its pending chunks) and `chunk` (one chunk: a named claim, a heartbeat every third of the TTL, `processChunk`, then the run's next advance). The app's worker owns the BullMQ `Worker` and calls `handle(job, { trace })` with each job. Rules:
  - At most one advancer per run: every advance is added with `deduplication: { id: 'advance-<runId>', keepLastIfActive: true }`, so one is active, one waits, and a submit that lands mid-advance becomes the next one, never lost.
  - A chunk job's id is `chunkJobId`: `chunk-` + sha1 of the chunk and its attempts, so a repeated dispatch is a no-op while its job exists and a retried or swept chunk gets a fresh one; its delay is the chunk's `runAt`. An advance dispatches a window of the run's pending chunks (`dispatchWindow`, default 64, due first) and skips each this process enqueued at the same id and `runAt` within `claimTtlMs`; the mark is forgotten when this process handles the chunk's job (skipped or not), so each chunk is enqueued about once per process rather than once per advance, and a job consumed without settling its chunk is enqueued again.
  - Retries have one owner, the engine (`RetryPolicy`) with the store's attempts: every job is added with `attempts: 1`, no BullMQ backoff, `removeOnComplete/Fail: true`. A chunk job that finds its chunk held, settled or not yet due is skipped.
  - `sweep()` is the backstop the app schedules: expired claims back to pending, then a page of open runs (`openRunIds(SWEEP_RUNS, after)`, 500) resubmitted, deduplicated so cheap. Each sweep continues past the last run the previous one resubmitted and starts over after a short page, so every open run is resubmitted within ⌈open / 500⌉ sweeps, however many runs of another version are left open. Where it left off (the open page and the due page) is a `SweepCursors` port (`sweepCursors`, page size `sweepRuns`): `memorySweepCursors()` by default, one process's own; `redisSweepCursors` (`@pattern-stack/jobs/redis`, on the limiters' structural `eval`) shares them, so the scheduled sweep continues on whichever worker it lands where the last one, on any worker, left off.
  - A run of a job this process doesn't register, or made by another definition version, is skipped with a warning (a rolling deploy: a process that has it takes it), except an advance of another version once this process is up past `versionGraceMs`, which fails the run (`JobVersionGoneError`); any other error fails the job.
  - Every context on an engine job is its own run's trace root, never a caller's: `submit` and `sweep()` enqueue with none, so the worker opens the run's root; a handled job stamps every job it enqueues with the context it arrived with, or the `trace` its caller passed to `handle(job, { trace })` (the root the worker opened for it) when it had none. A deduplicated advance therefore only ever coalesces its own run's root, or none.
  - A new executor accepts jobs (a booting worker may fetch some before the app is up); `stop()` stops accepting and `start()` resumes; `stop({ drain: false })` also aborts in-flight chunks, each giving back only its own claim. Heartbeats run until each in-flight chunk settles.
  - Its limiters are the `Limiters` it is given (`options.limiters`); the default, `localLimiters()`, is per process, so N worker replicas get N times each quota. The app hands in `redisLimiters` for one quota across workers.

## What the package never imports

The core's only runtime dependency is `zod` (`./nest` adds its optional Nest and OpenTelemetry peers); it may use Node built-ins, and it is built against Node's types only (`types: ["node"]`), so a Bun-only global doesn't compile. `src/__tests__/fences.test.ts` holds the fences: the core (`model`, `ports`, `policy`, `define`, `engine`, `adapters`, `shapes`, `testing` and the `.`, `./ports`, `./testing`, `./shapes` barrels) imports only `zod` and its own files (the testing layer may read Node built-ins, the in-memory adapters `node:crypto`); `@nestjs/*` and `@opentelemetry/*` only under `src/nest/` and `src/nest.ts`, `drizzle-orm` only under `src/postgres/`, `bullmq` only under `src/bullmq/`; `src/redis/` imports nothing outside the core (its client is structural); nothing imports a `@repo/*` or `@pattern-stack/*` package (its own name included); the core never imports an adapter path; production code never imports the testing layer. The tables are the host's (codegen emits them) and are handed to the store.
