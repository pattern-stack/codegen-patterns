# S-1: events under `wiring: pattern-stack`

**Status:** implemented · **Follows:** PW-EAV · **Plan:** codegen-targets `docs/PLAN-platform-lane.md` §2 (Events)

## Problem

PW-3a refused `emits:` under pattern-stack wiring.
- **Runtime.** The event bus backends were Nest providers: `@Injectable`, `@Inject` tokens, Nest's `Logger`, and
  the drain loop started in `onModuleInit`. The events barrel re-exports `EventsModule`.
- **Generated code.** The typed bus (`generated/bus.ts`) is decorated. The use cases that publish inject
  `DRIZZLE` and `TYPED_EVENT_BUS`. The delete use case throws Nest's `NotFoundException`.
- **The PW-0 known gap.** The package-mode registry augmentation targets `…/events/index`, which loads the Nest
  module.

Nothing composed an event bus without Nest, so nothing drained events in a pattern-stack app.

## Decision

### Runtime: one bus, two hosts

- `DrizzleEventBus` and `MemoryEventBus` are plain classes. Their constructors take `(db, options?, bridgeHook?)` and
  `(options?)`. They log through the logger port, and they have `start()` / `stop()`: the drain loop and the LISTEN
  wake listener. The memory bus's are no-ops.
- `onModuleInit` / `onModuleDestroy` stay as one-line delegates, so Nest runs them.
- `EventsModule.forRoot` builds both through `useFactory`, with the bridge hook injected as optional, as
  `forRootAsync` already did. The Nest behaviour is the same; the integration suite holds it.
- `EventsModuleOptions` moved to `events-options.ts`, which is Nest-free. `events.module.ts` and `events/core`
  re-export it.
- The Nest-free gate (`nest-free.test.ts`) adds both backends as entries, so their import closure is checked too.
- The backends are not exported from `core.ts`, because a memory install prunes the drizzle backend. The `events`
  system imports the selected one by path.

### `subsystem install` under pattern-stack

- Only events, on drizzle or memory. Every other subsystem is refused, naming its step: auth S-2, integration S-3,
  jobs and bridge J-1. Redis is refused because it is Nest-only.
- The vendored copy skips `events.module.ts`, the `index.ts` barrel (it re-exports the module) and the bundled
  `generated/` set (its bus is Nest's). The `entity new` that follows writes the pattern-stack `generated/` files.
- No Nest subsystem barrel: `regenerateSubsystemBarrel` refreshes only `app-config.ts` under pattern-stack. The
  subsystem schema barrel is regenerated, so `domain_events` reaches drizzle-kit.
- The install writes the empty pattern-stack event set (both modes, never over a generated one). So a command that
  writes the composition before the first `entity new` (`junction new`, say) leaves an `events-system.ts` whose import
  resolves.
- `openapi-config` is allowed: it is config-only.
- The next step it prints names the two lines an older project adds by hand: `...SYSTEMS` in `compose.ts`, and
  `subsystems-schema.ts` in `drizzle.config.ts`. (`project init` writes both, but the project owns those files.)
- Vendored detection keys the events install on `core.ts` under pattern-stack. (Under Nest it keys on
  `events.module.ts`, and `project init` already vendors the protocol, so the directory alone doesn't count.)

### `entity new` under pattern-stack, with events installed

- **The event codegen** runs with `wiring: 'pattern-stack'`:
  - the bus has no decorators and no tokens, and the `events` system constructs it with `(bus, multiTenant = false)`;
  - package-mode imports and the `DomainEventRegistry` augmentation go through `…/events/core`. The interface is
    declared in `event-registry.ts`, and both entries re-export it, so the augmentation merges into the same one.
- **The subsystem schema barrel** re-exports `domainEvents` from `…/events/core`.
- **The composition** (`emitComposition`, its `events` input built by `patternStackEventsInput` from the config's
  `events:` block):
  - `<generated>/events-system.ts`. Its `eventsSystem` uses `database` (drizzle only). `create` builds the bus, the
    `TypedEventBus` and an `EventScheduler` over the registry's `schedule:` events.
    `start` runs `bus.start()`, then the scheduler; `stop` reverses that. If the scheduler fails to start, `start`
    stops the bus before rethrowing, because compose does not stop a part whose start failed. `EventsApi` is
    `{ bus, typed, scheduler }`.
  - `SystemApis` gains `events: EventsApi`. `<generated>/composition.ts` exports `SYSTEMS = [eventsSystem]`, or `[]`
    without events.
  - A module whose entities have a publishing use case (the class graph's `typed_event_bus` system, PW-1) has
    `uses: ['database', 'events']`. Its deps add `events: EventsApi`, and the entity's services get `db` and
    `typedEvents: deps.events.typed`.
  - A publishing entity with events not installed is refused, naming `codegen subsystem install events`.
  - `events-system.ts` is a stale wiring file once events is uninstalled, or under nest.
- **Templates.** The five publishing use-case branches (create, update and delete, plus the EAV create and update):
  - drop the Nest import, the token imports and `@Inject(…)` under pattern-stack, and import
    `type { TypedEventBus }` from the generated bus;
  - delete throws `NotFoundError` there.
  The Nest text is unchanged byte for byte. `typedEventBusImport` (vendored) is
  `@shared/subsystems/events/generated/bus` under pattern-stack.
- **`<entity>.wiring.ts`.** `patternStackWiringParts.events` (the publishing use-case kinds and the bus import) adds
  `db` and `typedEvents` to the service deps. Each publishing use case is built `(service, db, typedEvents)`, or
  `(service, fieldValues, db, typedEvents)` under EAV.
- The `emits:` refusal is lifted.
- `entity new --dry-run` lists the event set and the schema barrel it would write (JSON: `events`).

### Why start and stop belong to the system

`events.module.ts` records the scheduler bug. A boot tick drained before the bridge attached its outbox hook, and
deliveries were lost (swe-brain, 0.20.1). The Nest fix was to wait for `onApplicationBootstrap`. In the wiring every
hook attaches during `create`, and `start` runs only after every `create`, so the ordering holds by construction.

### `project init`

`compose.ts` composes `[databaseSystem(url), ...SYSTEMS]`. `drizzle.config.ts` reads both the entity schema barrel and
`<generated>/subsystems-schema.ts`, which init writes empty.

### Also removed

PW-EAV's EAV + `inherits:` refusal could never fire, because the schema refuses EAV on a family member (R9).

## Not in this step

- **Lifecycle events.** Under Nest the untyped `BaseService` lifecycle events are published through an optional
  `eventBus` property injection. Pattern-stack services get no bus. An app that wants them declares `emits:`.
- **The bridge outbox hook.** `bridgeHook` is a constructor argument the events system doesn't pass (the bridge is
  J-1).
- **Redis, and every other subsystem.**

## The gate

`test-smoke-pattern-stack`:
- installs events (drizzle) after init, and asserts the vendored Nest-free closure and no module, barrel or
  `subsystems.ts`;
- gives `invoice` `emits: [invoice_created]`, and asserts that `events-system.ts` and the generated bus exist and that
  billing's module uses `events`;
- checks that `main.ts` composes `database, events, …`;
- on Postgres, `crud-check` subscribes to `invoice_created` on `app.system('events').typed`, creates an invoice, and
  waits for the drain to deliver the payload.

The Nest-free gate covers both backends. Unit tests: `events-pattern-stack.test.ts` (the bus, the augmentation, the
schema barrel, the install refusals, the file filter), `emit-composition.test.ts` (the events system, `SYSTEMS`,
`SystemApis`, the module's `uses` and deps, the refusal, the memory backend), and `project.test.ts` (init's
`compose.ts` and `drizzle.config.ts`). The Nest output is held by the baseline, the render goldens, the
integration-emit goldens and every Nest smoke.
