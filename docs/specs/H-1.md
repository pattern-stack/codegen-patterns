# H-1: commands, and Hono routes as views of them

**Status:** spec · **Follows:** SET-1 (#982) · **Brief:** codegen-targets `docs/LANE-hono.md`, `docs/PLAN-platform-lane.md`
§3, §4, §5

## Problem

Under `target: { wiring: pattern-stack }` an app has its use cases, composed with `@pattern-stack/wiring`, and no way
in from outside: `http: none` is the only HTTP value, and the controllers are Nest's. The platform needs an HTTP layer
without Nest, and later MCP tools (C-1) and a CLI (C-2) over the same operations.

The operations are already listed once (`apiSurface.useCases`, and every `Route` names its use case). What's missing is
one uniform way to call one: a name, one input object, a result or a refusal. Without it, each way in (HTTP now, MCP and
a CLI later) re-binds its own input and re-translates errors.

Doug's calls (2026-11-27): request state through `AsyncLocalStorage`, with no per-request scope in the wiring; commands
built inside H-1, with routes as views of them; OpenAPI from codegen's registry; runtime-neutral output (Bun and Node);
idempotency keys on side-effect commands.

## Decision

### A command per use case

`src/derived/api` gains `commands`, one per routed use case (every `Route.useCase`), derived once with provenance like
the rest of the surface (ADR-046):

| Field | Example | Rule |
|---|---|---|
| `name` | `contact create`, `contact find` | entity (kebab) + the kind's verb: `find_by_id` → `find`, `list`, `create`, `update`, `delete`, `search`, `find_by_id_with_fields` → `find-with-fields`, `list_with_fields` → `list-with-fields` |
| `useCase` | `CreateContactUseCase` | the use case it runs |
| `effect` | `side-effect` | find / list / search: `read`; update: `idempotent`; create / delete: `side-effect` |
| `input` | `{ id, ...UpdateContactDto }` | one flat object: the DTO's fields, plus `id` and `include` where the use case takes them |
| `binding` | `{ path: ['id'], query: ['include'], body: '*' }` | which input fields an HTTP request carries where; MCP and the CLI ignore it |
| `success` | `201` | the HTTP status of a result: create 201, delete 204, else 200 |

A DTO field named `id` or `include` where the command also takes one is a generation error naming the field (the flat
input would collide). Declarative queries (`kind: 'query'`) have no route and get no command here; C-1 adds them when
there's a way in that calls them.

### `Command` and `Outcome` in `@pattern-stack/wiring`

`packages/wiring` gains a `/commands` export with crew's shapes (`crew:s4/src/core/kernel/command.ts`, `outcome.ts`):
`Command<Apis, I, T>` (`name`, `summary`, `input: z.ZodType`, `effect`, `run(apis, input, ctx)`), `Outcome<T>` (a result,
or a refusal `{ reason, detail, instead }`). Two additions crew lacks, both optional so crew's commands still fit:

- `effect: 'read' | 'idempotent' | 'side-effect'`, and `ctx.idempotencyKey`;
- `refusal.data`: structured fields a way in may print (the HTTP body's `code`, `path`, `fields`, `issues`).

The package keeps no dependencies: `input` is typed structurally (a `safeParse`), as `SettingsChecker` is.

### The emitted commands

Under pattern-stack wiring (either `http`), each entity gets `<entity>.commands.ts` beside its `.wiring.ts`, and
`<generated>/commands.ts` is the whole-set table (`COMMANDS`, printed from the derivation, never re-listed). A command's
`run(modules, input, ctx)` reaches its use case through the composed module (`modules.crm.contact.useCases.create`).

`run` is where the behaviour the Nest controller holds today moves, so every way in gets it:
1. parse `input` (Zod); a failure is refusal `invalid-input`, `data` = the `ZodValidationPipe` body (`issues[{path, code,
   message}]`). The issue paths are the DTO's own, because the input is flat;
2. resolve `include` against the route's allowlist (`resolveAllowedInclude`); a refused path is `include-not-allowed`
   with `data` = today's body (`code`, `path`);
3. run the use case. What it throws becomes a refusal by one table in a new `runtime/commands.ts`:
   `NotFoundError` → `not-found`, `BadRequestError` → `bad-request`, a constraint violation (`constraintViolationOf`)
   → `unique-violation` / `foreign-key-violation` / `still-referenced` with `data` = `constraintViolationBody`. Anything
   else is a crash and propagates;
4. update's `null` is `not-found` (the controller's `NotFoundException` today).

The 409/422 errors stay in `runtime/db-constraint-errors.ts` (their owner), not folded into `runtime/errors.ts`: the
table maps both owners' errors, so no body is restated.

### `target.http: hono`

`TARGET_APPS` gains `{ wiring: pattern-stack, http: hono }`. Under it, besides the commands:

- **`<entity>.routes.ts`** (`routes.ejs.t`, the twin of `controller.ejs.t`; the search route goes in the same file
  rather than a `search-routes.ejs.t`, since it is one more view of one more command). Each route: check `:id` as
  `ParseUUIDPipe` does (its 400 body), bind path / query / body onto the input by the command's `binding`, `run`,
  answer `success` or the refusal. Skipped on the same `!apiSurface.http.enabled`, so `api: false` has no routes.
- **`runtime/http/hono/`** (`hono` an optional peer, added to the Nest-free gate's ENTRIES): `answer(c, outcome,
  success)`, the one refusal → status table (`invalid-input`, `bad-request`, `include-not-allowed` → 400, `not-found` →
  404, `unique-violation`, `still-referenced` → 409, `foreign-key-violation` → 422), the body being `refusal.data` (the
  Nest bodies, byte for byte); and `onError`, a 500 with Nest's body for a crash. No separate `validate` middleware (the
  plan's §3): validation is the command's, so it holds for MCP and the CLI too.
- **`<generated>/http.ts`**: `createApp(wired)` returns a `Hono` with every entity's routes, `/docs-json`, and `onError`.
  Whole-set, composed from the derivation.
- **OpenAPI paths.** `<generated>/openapi.ts` gains `registerOpenApiPaths(openApi)`: `registerPath` for every derived
  route, with the operationId, verb, path, the DTO `$ref`s and the include / paging parameters the controller's
  decorators name today. The text the decorators hold (summaries, parameter descriptions, response statuses) moves
  into the derivation's route record so both targets print it from one place. Nest's output stays byte-identical.
- **`project init --wiring pattern-stack --http hono`**: `main.ts` composes, starts, and serves `createApp(wired)` with
  `@hono/node-server` (it runs on Bun and Node, so the output is runtime-neutral; H-3 proves both), and stops on SIGTERM.

Request state (`AsyncLocalStorage`, `withRequester`) is H-2's; H-1's routes run outside any requester, as the
pattern-stack use cases do today.

### Idempotency

A `side-effect` command with `ctx.idempotencyKey` stores its outcome per key, in a table codegen emits
(`command_outcomes`: key, command name, outcome JSON, created_at), and a repeat with the same key returns the stored
outcome without running. HTTP passes the `Idempotency-Key` header. A key reused for another command is refusal
`idempotency-key-reused`.

## Open (for the PM / Doug)

1. **No `validate` middleware** (a change from the plan's §3): validation lives in the command. Same 400 body.
2. **Search shares `routes.ejs.t`** rather than a `search-routes.ejs.t` twin. One view file per entity.
3. **Declarative queries get no command in H-1** (they have no route); C-1 adds them.
4. **The decorator text moves into the derivation** (summaries, descriptions, response codes) so the OpenAPI paths and
   the Nest decorators print from one place. Byte-identical for Nest, but it touches `controller.ejs.t`; the
   alternative is restating that text in the Hono OpenAPI printer, which the parity gate would then hold equal.
5. **Idempotency storage is a generated table** (`command_outcomes`) in the app's database, so a stored outcome commits
   with nothing else: a crash between the effect and the record re-runs the effect once. Writing the record in the use
   case's transaction closes that, but needs every side-effect use case to take a transaction handle. H-1d picks; the
   default is the separate table.
