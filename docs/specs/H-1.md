# H-1: commands, and Hono routes as views of them

**Status:** H-1a, H-1b implemented; OpenAPI paths, H-1c, H-1d spec · **Follows:** SET-1 (#982) · **Brief:** codegen-targets `docs/LANE-hono.md`, `docs/PLAN-platform-lane.md`
§3, §4, §5

## Problem

Under `target: { wiring: pattern-stack }` an app has its use cases, composed with `@pattern-stack/wiring`, and no way
in from outside: `http: none` is the only HTTP value, and the controllers are Nest's. The platform needs an HTTP layer
without Nest, and later MCP tools (C-1) and a CLI (C-2) over the same operations.

The operations are already listed once (`apiSurface.useCases`, and every `Route` names its use case). What's missing is
one uniform way to call one: a name, one input object, a result or a refusal. Without it, each way in (HTTP now, MCP and
a CLI later) re-binds its own input and re-translates errors.

Doug's calls (2026-11-27): request state through `AsyncLocalStorage`, with no per-request scope in the wiring; commands
built inside H-1, with routes as views of them; OpenAPI from codegen's registry; runtime-neutral output (Bun and Node);
idempotency keys on side-effect commands.

## Decision

### A command per use case

`src/derived/api` gains `commands` (and `commandsConst`, the export that lists them), one per use case but a declarative
query, routed or not (an `api: false` entity's commands have no `http`, so MCP and a CLI can still call them), derived
once with provenance like the rest of the surface (ADR-046):

| Field | Example | Rule |
|---|---|---|
| `name` | `contact create`, `contact find` | entity (kebab) + the kind's verb: `find_by_id` → `find`, `list`, `create`, `update`, `delete`, `search`, `find_by_id_with_fields` → `find-with-fields`, `list_with_fields` → `list-with-fields` |
| `useCase` | `CreateContactUseCase` | the use case it runs |
| `effect` | `side-effect` | find / list / search: `read`; update: `idempotent`; create / delete: `side-effect` |
| `input` | `{ id, ...UpdateContactDto }` | one flat object: the DTO's fields, plus `id` and `include` where the use case takes them |
| `includeRoute` | `find_by_id` | the `api.includes` key the include resolves against; absent ⇒ every include is refused |
| `http` | `{ verb, path, binding: { path: ['id'], query: ['include'], body: false }, success: 200 }` | present when routed: which input fields the path, the query (`'all'` for list and search) and the body carry, and a result's status: the one Nest sends for the verb (`NEST_SUCCESS_STATUS`, from Nest's `getStatusByMethod`: POST 201, else 200; the controllers set no `@HttpCode`, so a delete is 200 with an empty body) |

A generated DTO never has an `id` (the database makes it) or an `include` key, so the flat input can't collide. Declarative queries (`kind: 'query'`) have no route and get no command here; C-1 adds them when
there's a way in that calls them.

### `Command` and `Outcome` in `@pattern-stack/wiring`

`packages/wiring` gains a `/commands` export with crew's shapes (`crew:s4/src/core/kernel/command.ts`, `outcome.ts`):
`Command<Apis, I, T>` (`name`, `summary`, `input: z.ZodType`, `effect`, `run(apis, input, ctx)`), `Outcome<T>` (a result,
or a refusal `{ reason, detail, instead }`). Two additions crew lacks, both optional so crew's commands still fit:

- `effect: 'read' | 'idempotent' | 'side-effect'`, and `ctx.idempotencyKey`;
- `refusal.data`: structured fields a way in may print (the HTTP body's `code`, `path`, `fields`, `issues`).

`onApis(command, select)` re-targets a command onto a larger set of APIs, and `allOnApis` a list of them (typed
loosely, for a table).

The package keeps no dependencies: `input` is typed structurally (a `safeParse`), as `SettingsChecker` is.

### The emitted commands

Under pattern-stack wiring (either `http`), each entity gets `<entity>.commands.ts` beside its `.wiring.ts`: its
commands (`contactCommands`), each run on the entity's use cases. `<generated>/commands.ts` is the whole-set table:
`COMMANDS` (each entity's, re-targeted onto the composed app with `allOnApis`, reaching its use cases through its
context's module, `app.module('crm').contact.useCases`) and `commandNamed(name)`. A way in calls
`invokeCommand(command, app, rawInput, ctx)` (`runtime/commands.ts`), which parses the input before `run`.
`wiringFilesBehind` names an entity whose `.commands.ts` is missing, and the switch to Nest removes both files.

`run` is where the behaviour the Nest controller holds today moves, so every way in gets it:
1. parse `input` (Zod, in `invokeCommand`); a failure is refusal `invalid-input`, `data` = the body
   `ZodValidationPipe` throws, now built once in `runtime/validation-error.ts` (`validationErrorBody`) for both. The
   issue paths are the DTO's own, because the input is flat;
2. resolve `include` against the route's allowlist (`resolveAllowedInclude`); a refused path is `include-not-allowed`
   with `data` = today's body (`code`, `path`);
3. run the use case. What it throws becomes a refusal by one table in a new `runtime/commands.ts`:
   `NotFoundError` → `not-found`, `BadRequestError` → `bad-request`, a constraint violation (`constraintViolationOf`)
   → `unique-violation` / `foreign-key-violation` / `still-referenced` with `data` = `constraintViolationBody`. Anything
   else is a crash and propagates;
4. update's `null` is `not-found` (the controller's `NotFoundException` today).

The 409/422 errors stay in `runtime/db-constraint-errors.ts` (their owner), not folded into `runtime/errors.ts`: the
table maps both owners' errors, so no body is restated.

### `target.http: hono`

`TARGET_APPS` gains `{ wiring: pattern-stack, http: hono }`. Under it, besides the commands:

- **`<entity>.routes.ts`** (`routes.ejs.t`, the twin of `controller.ejs.t`; the search route goes in the same file
  rather than a `search-routes.ejs.t`, since it is one more view of one more command). Each route: check `:id` as
  `ParseUUIDPipe` does (its 400 body), bind path / query / body onto the input by the command's `binding`, `run`,
  answer `success` or the refusal. Skipped on the same `!apiSurface.http.enabled`, so `api: false` has no routes.
- **`runtime/http/hono/`** (`hono` an optional peer, added to the Nest-free gate's ENTRIES): `answer(c, outcome,
  success)`, the one refusal → status table (`invalid-input`, `bad-request`, `include-not-allowed` → 400, `not-found` →
  404, `unique-violation`, `still-referenced` → 409, `foreign-key-violation` → 422), the body being `refusal.data` (the
  Nest bodies, byte for byte); and `onError`, a 500 with Nest's body for a crash. No separate `validate` middleware (the
  plan's §3): validation is the command's, so it holds for MCP and the CLI too.
- **`<generated>/http.ts`**: `createApp(wired)` returns a `Hono` with every entity's routes, `/docs-json`, and `onError`.
  Whole-set, composed from the derivation.
- **OpenAPI paths.** `<generated>/openapi.ts` gains `registerOpenApiPaths(openApi)`: `registerPath` for every derived
  route, with the operationId, verb, path, the DTO `$ref`s and the include / paging parameters the controller's
  decorators name today. The text the decorators hold (summaries, parameter descriptions, response statuses) moves
  into the derivation's route record so both targets print it from one place. Nest's output stays byte-identical.
- **`project init --wiring pattern-stack --http hono`**: `main.ts` composes, starts, and serves `createApp(wired)` with
  `@hono/node-server` (it runs on Bun and Node, so the output is runtime-neutral; H-3 proves both), and stops on SIGTERM.

Request state (`AsyncLocalStorage`, `withRequester`) is H-2's; H-1's routes run outside any requester, as the
pattern-stack use cases do today.

### Idempotency

A `side-effect` command with `ctx.idempotencyKey` stores its outcome per key, in a table codegen emits
(`command_outcomes`: key, command name, outcome JSON, created_at), and a repeat with the same key returns the stored
outcome without running. HTTP passes the `Idempotency-Key` header. A key reused for another command is refusal
`idempotency-key-reused`.

## Open (for the PM / Doug)

1. **No `validate` middleware** (a change from the plan's §3): validation lives in the command. Same 400 body.
2. **Search shares `routes.ejs.t`** rather than a `search-routes.ejs.t` twin. One view file per entity.
3. **Declarative queries get no command in H-1** (they have no route); C-1 adds them.
4. **The decorator text moves into the derivation** (summaries, descriptions, response codes) so the OpenAPI paths and
   the Nest decorators print from one place. Byte-identical for Nest, but it touches `controller.ejs.t`; the
   alternative is restating that text in the Hono OpenAPI printer, which the parity gate would then hold equal.
5. **Idempotency storage is a generated table** (`command_outcomes`) in the app's database, so a stored outcome commits
   with nothing else: a crash between the effect and the record re-runs the effect once. Writing the record in the use
   case's transaction closes that, but needs every side-effect use case to take a transaction handle. **PM
   (2026-11-27): record it in the use case's own transaction when it runs in one** (agents call side-effect commands
   as tools; a re-run effect after a crash is what the key exists to prevent). If H-1d can't do that cleanly, it says
   why and the PM takes it to Doug. Calls 1–4: approved.

6. **Which commands are exposed, and to whom** (open, for the MCP step C-1; not H-1b). H-1a derives a command for
   every use case, `api: false` entities included, so a way in that lists `COMMANDS` (MCP, a CLI) would offer generic
   reads that cross workspaces (identity's user, workspace and membership). Before C-1: a per-entity switch in the
   command derivation (from the YAML, never a name check; the identity lane needs it first), and a rule for which
   commands each way in exposes, and to which requester (H-2's port). HTTP is unaffected: routes exist only where
   `api:` is on.

## As built (H-1a)

- The search's filters schema is printed by both the Nest search controller and the search command from one list of
  lines, `searchQuery.filtersSchemaFields` (`entity-locals.js`); the controller's bytes are unchanged.
- The list command passes its whole parsed input (the include too) to the use case, as the Nest controller passes its
  query; the find and list commands resolve the include inside `attempt`, so a refused one is a refusal.
- `@pattern-stack/wiring` is a root dev dependency (`workspace:*`). `just typecheck` depends on `build-wiring` (as on
  `build-jobs`): the root typecheck resolves `@pattern-stack/wiring/commands` to its `dist` types.
  The runtime imports only its types, so a Nest project that never loads `runtime/commands.ts` needs nothing new.
- A malformed `id` is `invalid-input` from a command (its `z.guid()`); over HTTP the route checks `:id` first, as
  `ParseUUIDPipe` does, so the body there is still Nest's (H-1b).
- `ctx.idempotencyKey` is carried but not read until H-1d.
- Proof: `test/smoke/fixtures-pattern-stack-usage/crud-check.ts`'s `commandsCheck`, on Postgres: create, find, list,
  search, and each refusal (`invalid-input`, `include-not-allowed`, `not-found` on update and find,
  `foreign-key-violation`, `still-referenced`), the bodies compared to Nest's.

### #986 review (as fixed)

- A routed command's success status is `NEST_SUCCESS_STATUS[verb]` (Nest's own rule), and the test reads Nest's
  `RouterResponseController.getStatusByMethod` and holds the controllers to having no `@HttpCode`.
- `commands.ejs.t` prints each input from the derived `input` (a base schema by `dto` / `query`, plus `id` and
  `include`); only the use-case call is per kind. `COMMAND_SHAPES` holds each kind's include key and HTTP binding.
- One use-case key rule (`useCaseKey`), read by the wiring and the commands; one path rule for an entity's
  pattern-stack files (`entityModuleNaming`: `wiringFile`, `commandsFile`), with the per-wiring outputs a table keyed
  by `target.wiring`.
- The Nest controller prints its `@ApiOperation` summaries from the commands, and both targets print a missing row's
  message from `apiSurface.notFoundMessage`. A refusal's reason for an application error is `APP_ERROR_REASONS[status]`;
  a search filter's Zod chain is `FILTER_CHAINS[kind]`; the derived effect is the wiring package's `Effect`.

## As built (H-1b)

- **The layer is a registry (Doug's rule).** `TARGET_APPS` gains `{ wiring: pattern-stack, http: hono }`.
  `HTTP_LAYERS` (`src/targets/http.ts`) has one data row per `target.http` value (`nest` and `none` are null): the
  routes-file suffix, the runtime files it vendors, the runtime module it imports, the packages it installs, and its
  settings. `HTTP_RENDERERS` (`src/emitters/http/`) holds each layer's text (`<generated>/http.ts`, `main.ts`), typed
  so a layer without one is a `tsc` error. Readers go through `rowFor`; none branches on the value.
- **Routes** (`routes.ejs.t` → `<entity>.routes.ts`, `<entity>Routes(useCases)`, a name the derivation gives as
  `http.routesFunction`): static paths are registered before `/:id`, so `/accounts/search` is never read as an id. A
  route checks `:id` as `ParseUUIDPipe` does (`badId`), reads the body as Express's `body-parser.json` (strict) does
  (`jsonBody`: only `application/json` is parsed, else `{}`; an empty body is `{}`; a top level that isn't an object or
  array, or malformed JSON, is a 400 with the parser's message), reads the query as Express does for a flat query
  (`queryOf`: a repeated key is an array), binds path, query and body onto the input (`bindInput`), and answers with
  `answer`: the success status (a create 201, else 200; a command with no result, a delete, answers an empty body as
  Nest's void handler does), or the refusal's body with the status that body names (its error owner's `statusCode`, so the status can't drift
  from the body; no status table of its own). An `api: false` entity has none,
  and neither has one whose generated commands are off (`generate.commands: false`, ID-1's `commandsDisabledBy`):
  routes are views of commands, so `http.ts` mounts only entities with both.
- **Known differences from the Nest target**, each named so the parity gate (H-1c) masks or skips it, not hides it:
  a malformed-JSON 400's `message` is the JS runtime's `JSON.parse` text (Bun's and Node's differ; Nest runs on
  Node); bracket query keys (`a[b]=1`) are not nested (the generated queries have none); paths are case-sensitive
  (Express's are not: `GET /Accounts` lists on Nest, 404s here). A trailing slash is ignored, as Express ignores it
  (`new Hono({ strict: false })`), and a body over 100kb is a 413 with Nest's body before it is read
  (`useNestBodyLimit`, body-parser's default limit).
- **`<generated>/http.ts`**: `createApp(app, { openApi })` mounts each routed entity on its module's use cases, serves
  `/docs-json` (the registry's components; paths are H-1b2), and installs Nest's unknown-route 404 and crash 500
  (`useNestFallbacks`; a crash is logged through `createLogger`).
- **The port is a setting** (SET-1): the Hono row declares `http.port` (`PORT`, default `3000`, a new `port` format:
  1 to 65535, checked when the app composes), so it is in
  `<generated>/settings.ts`, `.env.example` and `codegen project settings`. `main.ts` serves on it with
  `@hono/node-server` (Bun and Node) and stops on SIGINT / SIGTERM: the server closes, then the composition stops.
- **`project init --http hono`** (implies `--wiring pattern-stack`; an unsupported pair is refused naming the rows; an
  `--http` the existing config doesn't say is refused, as a mismatched `--wiring` is; `main.ts` is a row per `http`
  value, `PATTERN_STACK_MAINS`)
  writes the target, the served `main.ts`, `http.ts` over no entity, the Hono runtime (vendored only with its layer;
  `project update` re-syncs it and removes another layer's), and prints the layer's packages. A routes file is removed when the target's layer no
  longer owns its suffix.
- **Proof:** `just test-smoke-hono` (in `test-all`): init, two entities, no `@nestjs`, `tsc`, `main.ts` serves
  `/docs-json` and stops on SIGTERM. Its Postgres leg (in `test-integration`) runs `fixtures-hono-usage/http-check.ts`
  through `createApp(app).request(…)`: create, find, list, search, update, delete (200, empty body, as Nest), and every refusal and
  fallback with the Nest body (`ParseUUIDPipe`, 404s, include, validation, malformed JSON, 422, 409, unknown route).
