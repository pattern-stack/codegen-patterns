# S-2: auth under `wiring: pattern-stack`

**Status:** implemented · **Follows:** SET-1 · **Plan:** codegen-targets `docs/PLAN-platform-lane.md` §2 (Auth)

## Problem

S-1 refuses `subsystem install auth` and `subsystem install auth-integrations` under pattern-stack wiring.
- **Runtime.** Auth's non-HTTP half is plain already (PW-0's `auth/core`): the protocols, the AES-GCM encryption key,
  both OAuth state stores and the refresh strategy. Two gaps remain. `EnvEncryptionKey` reads `process.env` itself,
  so it can't take the `settings` system's value. And the callback URL a provider redirects to is built inside the
  Nest controller (`redirectUriFor`).
- **The install.** It copies the Nest half too (the module, the barrel, the controller, the guard, the
  requester-context middleware), and it appends an `AuthModule` TODO to `app.module.ts`, which a pattern-stack project
  doesn't have.
- **The connection store.** The `auth-integrations` starter (`examples/auth-integrations/`) is the connection store:
  three adapters for the auth ports (reader, token writer, grant sink), a facade and four use cases over the generated
  `connection` entity. Every class is `@Injectable()` with `@Inject(ENCRYPTION_KEY)`, and `ConnectionsAuthModule`
  binds them under Nest tokens.
- **Refresh.** An `OAuth2RefreshStrategy` takes the connection reader and token writer. Under pattern-stack, S-3's
  author-owned provider factory builds the strategy, and it has neither to give it.

So a pattern-stack app can't store a connection, run an OAuth state dance or refresh a token.

## Decision

### Runtime: one text owner

- `EnvEncryptionKey` takes `{ key }`, the base64 value itself, as well as `{ env, envVar }`. Same validation and the
  same error, naming `INTEGRATION_TOKEN_ENCRYPTION_KEY`. The `auth` system passes `settings.auth.tokenEncryptionKey`.
- `oauthCallbackUrl(redirectUriBase, provider)` (`runtime/subsystems/auth/runtime/oauth-callback-url.ts`, exported
  from `core`) builds `<base>/auth/<provider>/callback`. `AuthController.redirectUriFor` calls it, so the Nest bytes on
  the wire don't change.
- The starter's classes lose `@Injectable()` and `@Inject`. They take a structural `ConnectionRows` port
  (`connections/connection-rows.ts`: `findById`, `findByUserIdAndProvider`, `findByUserId`, `create`, `update`) that
  the generated `ConnectionService` and `ConnectionRepository` both satisfy, plus the `IEncryptionKey`.
  `createConnectionStore(rows, encryption)` (`connections/connection-store.ts`) builds all eight and returns
  `ConnectionStore`: `{ reader, tokenWriter, grantSink, connections }` (`connections` is the facade).
  `ConnectionsAuthModule` builds them with one `useFactory` over `ConnectionService` and `ENCRYPTION_KEY`, and binds
  the three tokens and `ConnectionsService` to its parts. So the Nest module's exports and token bindings don't change.

### `subsystem install auth` under pattern-stack

- Allowed. The OAuth state store is the Drizzle one (`auth_oauth_state`). `--backend memory` is refused: one process's
  memory can't hold a state that a callback on another replica consumes.
- The vendored copy skips the Nest half: `auth.module.ts`, `index.ts`, `controllers/`, `guards/` and
  `middleware/requester-context.ts`. The closure that's left is `core.ts`'s.
- The `app.module.ts` TODO isn't written. The `auth:` config block, the `auth_oauth_state` schema and the
  `.env.config` lines (the key and the redirect base) are written as under Nest.
- The subsystem schema barrel re-exports `authOAuthState` from `…/auth/core` under pattern-stack, so drizzle-kit
  creates the table. Nest's barrel is unchanged (its gap is #284).
- Vendored detection keys on `core.ts` under pattern-stack, as events and integration do.
- The next step it prints names the `auth` system and `subsystems-schema.ts`.

### The `auth` system

`<generated>/auth-system.ts`, written by the composition when auth is installed:

```ts
export interface AuthApi {
  encryptionKey: IEncryptionKey;
  oauthState: IOAuthStateStore;
  /** The URL a provider redirects back to: `<auth.redirectUriBase>/auth/<provider>/callback`. */
  callbackUrl(provider: string): string;
}
export const authSystem = defineSystem({
  name: 'auth',
  uses: ['settings', 'database'],
  create: ({ settings, database }): AuthApi => ({ … }),
});
```

It has no start or stop. `SystemApis` gains `auth: AuthApi`, and `SYSTEMS` lists it after `integration`.

### `subsystem install auth-integrations` under pattern-stack

- Allowed once auth is installed. It's refused without it, naming `codegen subsystem install auth`.
- It vendors the starter and `connection.yaml` as under Nest, minus `connections-auth.module.ts`. The bare auth imports
  are rewritten to the Nest-free entry (`<subsystems>/auth/core`, or `…/runtime/subsystems/auth/core` in package mode).
- Detection keys on `connections/connection-store.ts` under pattern-stack (`CONNECTION_STORE_FILE`, the row's
  entry), on `CONNECTIONS_AUTH_MODULE_FILE` under Nest.
- No `app.module.ts` TODO is written.
- How the starter installs is one row per wiring (`AUTH_INTEGRATIONS_INSTALL`: the files skipped, the auth entry the
  imports point at, the package-mode specifier, the TODO), and auth's and auth-integrations' install support are rows
  of S-1's `PATTERN_STACK_SUBSYSTEMS`. auth's `authOAuthState` is in the schema barrel's symbol table, and the barrel's
  order is keyed by wiring (Nest's leaves auth out).
- `auth` and `connections` are generated system names (`GENERATED_SYSTEM_NAMES`), so a context with either name is
  refused at generation, not at `compose()`.

### The `connections` system

`<generated>/connections-system.ts`, written when the starter is vendored and `connection` is generated:

```ts
export const connectionsSystem = defineSystem({
  name: 'connections',
  uses: ['database', 'auth'],
  create: ({ database, auth }): ConnectionStore =>
    createConnectionStore(createConnectionRepository(database.db), auth.encryptionKey),
});
```

- **A system, not a module.** A provider's strategy refreshes through the reader and token writer, and a provider is a
  system (S-3); a system can't depend on a module. So the store builds its own `ConnectionRepository` from the
  generated `createConnectionRepository(db)`. A repository is stateless over `db`, and it reads the same request state,
  so it behaves the same as the instance in `connection`'s context module.
- `connection` must be buildable from `db` alone: no family, no EAV. Otherwise it's refused, naming the YAML.
  `belongs_to` edges don't matter, because the repository's constructor takes only `db`.
- With the starter vendored and no `connection` entity generated, the composition is refused, naming
  `codegen entity new connection`.
- `SystemApis` gains `connections: ConnectionStore`, after `auth`.

### Refresh: the provider factory takes the connection store

With the `connections` system composed, each provider system (S-3) `uses: ['settings', 'connections']`, and its
emit-once factory is written as
`create<P>Provider(settings: Settings['<group>'], connections: ConnectionStore)`. The comment shows the refresh
strategy's arguments:
`new SalesforceOAuthStrategy({ connectionReader: connections.reader, tokenWriter: connections.tokenWriter })`.
A factory written before the store was composed takes one parameter, and fails `tsc` against the system that now
passes two; there is no upgrade warning (no backwards compatibility until there are users, as SET-1). Without
`connections`, the factory and the provider system are as S-3 and SET-1 wrote them, byte for byte.

## Not in this step

- **HTTP (H-2):** the OAuth connect and callback routes, `IUserContext`, the requester-context middleware, the
  authenticated check and `STRATEGY_REGISTRY` (the routes build it from the provider systems).
- Sign-in, workspaces and membership (codegen-targets `docs/PLAN-identity.md`).
- The Nest schema barrel's `auth_oauth_state` gap (#284).
- `runtime: package` installs: as under Nest, a package-mode install records auth under `subsystems.install` but
  writes no `.env.config` line and no schema file (the state table comes from the package's `auth/core`). The key is set
  by hand; `codegen project settings --check` names it. The smoke runs vendored.

## The gate

- `test-smoke-pattern-stack` installs auth, then auth-integrations, after integration. It asserts the vendored
  Nest-free closure, that no auth module, barrel, controller, guard, middleware or `connections-auth.module.ts` was
  written, and that `auth-system.ts` and `connections-system.ts` exist. It checks that `main.ts` composes
  `settings, database, events, integration, auth, connections, …`. The key comes from the install's `.env.config`,
  which the settings system reads.
- On Postgres (the integration job), `crud-check`:
  - generates and consumes an OAuth state, and a second consume fails;
  - stores a grant through the grant sink, reads it back decrypted through the reader, and sees ciphertext in the row;
  - refreshes through an `OAuth2RefreshStrategy` subclass with a stubbed `fetch` over the system's reader and writer,
    and the rotated token is persisted;
  - checks that `callbackUrl('salesforce')` is the redirect base plus `/auth/salesforce/callback`.
- Unit tests:
  - the install: refusals (memory; auth-integrations without auth), the file filter, the import rewrite, detection;
  - the composition: both systems, `SYSTEMS`, `SystemApis`, the refusals;
  - the provider factory and system with and without `connections`;
  - `EnvEncryptionKey({ key })` and `oauthCallbackUrl`;
  - `createConnectionStore` against an in-memory `ConnectionRows`.
- Nest: the baseline, the goldens and every Nest smoke (`test-smoke-subsystems` installs both and boots) hold it.
