# J-1: jobs and the bridge under `wiring: pattern-stack`

**Status:** part 1 implemented (the runtime, the install and the settings); part 2 in progress (the generators and the
plain smoke) ·
**Follows:** JOBS-3 (#969), S-1, S-3, SET-1 · **Plan:** codegen-targets `docs/PLAN-platform-lane.md` (J-1) ·
**Brief:** codegen-targets `docs/LANE-jobs-on-wiring.md`

## Problem

JOBS-3 put generated Nest apps on `@pattern-stack/jobs`, but only through Nest:
- **Runtime.** `JobsEngineModule` composes the package's Nest `JobsModule` (the registry, the Postgres store, the
  sinks, the limiters, the in-process executor, the bootstrap check of job-factory dependencies through `ModuleRef`).
  `JobStarter` is `@Injectable()` over Nest tokens and logs through Nest's `Logger`. The bridge's
  `BridgeOutboxDrainHook` is the same, and checks its triggers in `onApplicationBootstrap`.
- **Install.** `subsystem install jobs` and `bridge` are refused under pattern-stack (S-1: "they come with J-1").
- **Generators.** Nothing composes the engine, nothing passes the bridge hook to the events system's bus (S-1 left it
  out), and a job factory's dependencies can only be resolved from a Nest container.

The platform app (Jarvis) has no NestJS, so it has no jobs.

## Decision

### Runtime: one engine, two hosts (part 1)

The S-1 / S-3 pattern: a framework-free class, and the Nest host as a thin decorated layer over it.

- **`JobRunStarter`** (`runtime/subsystems/jobs/job-run-starter.ts`) is `JobStarter`'s logic, framework-free. Its
  constructor takes its parts in one object: `{ registry, store, executor, tables, clock, events, around?, worker? }`.
  It logs through the logger port. `start(key, input, opts, tx?)` and `has(key)` are unchanged: the run's tenant
  (the caller's; omitted, the ambient requester's; else `SYSTEM_TENANT`), a run started in `tx` is created over a
  store on that transaction and not submitted, no submit when `worker` is false, a failed submit logged.
- **`JobStarter`** stays the Nest class: a decorated subclass whose constructor takes the same token-injected
  parameters and passes them to `super`, and whose `budget` override answers a refused budget with Nest's 400s
  (`budgetFor`), as before. The plain starter throws the package's `JobBudgetError` (`code: 'budget_required'` /
  `'budget_over_limit'`). Generated Nest output does not change.
- **The package's framework-free host parts** (`@pattern-stack/jobs/host`, a new export path): the budget rule
  (`resolveBudget`, `JobBudgetError`), the active-span sink and `fanOutSinks(sinks, warn)`, and the limiter boot check
  (`assertLimitersConfigured`). They lived in the Nest layer (`./nest`) under Nest's exceptions and `Logger`; that layer
  now wraps them (`budgetFor`, `fanOut`, `nestLogSink`) with the same behaviour. A path of its own, not the root,
  because the active-span sink imports `@opentelemetry/api` and the package's import fences keep the core to zod.
- **`createJobsEngine(options)`** (`runtime/subsystems/jobs/jobs-engine.ts`) builds what the package's Nest
  `JobsModule` builds for the in-process executor, without Nest: the registry (each `jobFactory` built with lazy
  dependencies), the Postgres store over the app's Drizzle client and the package's tables, the sinks (the active
  span, a log sink through the logger port, the store's event log), the in-memory limiters (checked against the
  registry, as the Nest module does), the `InProcessExecutor` with `tenantRunScope`, and a `JobRunStarter`. It
  returns `JobsEngine`:
  - `starter`, `registry`, `store`, `executor`;
  - `provide(factory, values)`: the values of one factory's dependencies, typed by the factory
    (`provide<D>(factory: JobFactory<D>, values: D)`), so a wrong part or a wrong type is a compile error in the
    generated code that calls it;
  - `start()`: checks that every factory's dependencies were provided (naming the job and the dependency), then starts
    the executor's loop when `worker` is true. The check comes first because compose does not stop a part whose start
    failed;
  - `stop()`: stops the loop and drains in-flight work. Idempotent.
- `buildJobs`' resolver takes a second argument, the entry and the dependency's name (`resolve(token, { entry, name })`),
  so a host can resolve per factory as well as per token. The Nest host ignores it.
- **The bridge.** `BridgeOutboxDrainer` (`bridge-outbox-drainer.ts`) is the drain hook's logic, framework-free: its
  constructor takes `(jobs: BridgeJobStarter, registry)` (`{ has, start }`, which both starters are), and `assertTriggersRegistered()` is the boot check (a trigger
  naming a job key this app does not register). `BridgeOutboxDrainHook` stays the Nest class, a decorated subclass
  whose `onApplicationBootstrap` calls the check.
- **Nest-free entries.** `runtime/subsystems/jobs/core.ts` exports the starter, the engine builder, `tenantRunScope`,
  the start options and the job tables; `runtime/subsystems/bridge/core.ts` exports the drainer, the protocol and
  `jobTriggers`, the errors, `assertTenantId` and the delivery schema. Each `index.ts` is `export * from './core'`
  plus its Nest half. Both entries join the Nest-free gate (`nest-free.test.ts`, through `NEST_FREE_SUBSYSTEMS`), which
  now also refuses `@pattern-stack/jobs/nest`, the package's Nest layer. The Nest modules call
  `useNestLogger()`, so the moved lines still print through Nest's `Logger`.

### `subsystem install jobs` / `bridge` under pattern-stack (part 1)

- Allowed. The refusals left are auth and auth-integrations (S-2) and events' Redis backend.
- The vendored copy skips each subsystem's Nest files: for jobs `jobs-engine.module.ts`, `job-starter.ts` and
  `index.ts`; for bridge `bridge.module.ts`, `bridge-outbox-drain-hook.ts`, `event-flow.service.ts`,
  `bridge.tokens.ts`, the delivery repository backends (only the Nest facade reads them) and `index.ts`.
- The jobs install writes no `worker.ts` and edits no `main.ts`: under pattern-stack the composition starts the
  executor, and a separate worker process is the same `main.ts` with `JOBS_WORKER=true` where the HTTP process has
  `false`.
- The config block is the same `jobs:` block (pools, poll interval, open-run sweep, version grace).
- Vendored detection keys the install on `core.ts`, as events and integration do.
- The bridge needs events on drizzle and jobs installed; the install says so and stops otherwise
  (`patternStackBridgePrerequisite`). The bridge's memory backend is refused under pattern-stack: the drain is the
  Drizzle outbox's.
- The next step it prints names the `jobs` system, `JOBS_WORKER`, and the schema barrel in `drizzle.config.ts`.

### Settings (part 1)

The jobs subsystem declares one setting in SET-1's table, under pattern-stack only (a Nest app reads its worker flag
from `main.ts` and `worker.ts`, so listing it there would name a variable nothing reads):

| Setting | Env | Default | Meaning |
|---|---|---|---|
| `jobs.worker` | `JOBS_WORKER` | `true` | whether this process runs the executor's loop; `false` in a process that only starts runs |

`format: 'boolean'` is new in `runtime/settings.ts`: the value is the string `true` or `false`, checked as one of the
two. The settings stay strings (`Settings['jobs']['worker']` is `string`); the system compares to `'true'`.

- **No `REDIS_URL`:** the in-process executor needs no Redis. It joins the table with the BullMQ executor, which codegen
  does not compose yet (JOBS-3, "Not yet").
- **No `LOG_LEVEL`:** the logger port reads none. It is the logger's, not the jobs subsystem's, and joins the table when
  the logger reads one.

### The composition (part 2)

- **The `jobs` system** (`<generated>/jobs-system.ts`): `uses: ['database', 'settings']`. `create` calls
  `createJobsEngine` with the app's Drizzle client, the generated `jobDefinitions`, the pools and the in-process
  options from `codegen.config.yaml`'s `jobs:` block, and `worker: settings.jobs.worker === 'true'`. `start` and
  `stop` are the engine's. `JobsApi` is `JobsEngine`; `SystemApis` gains `jobs: JobsApi`; `SYSTEMS` lists it after
  `settings` and before `events`.
- **A job factory's dependencies are composition parts.** Under pattern-stack there is no container, so a factory names
  each dependency by the part it is: `injected<IntegrationsModule>('integrations')`, a module or a system of the
  composition. `entity new` scans the factories (the registry scan) for those names. A class token is refused under
  pattern-stack, naming the job and the dependency.
- **The `jobDeps` module** (`<generated>/job-deps.ts`), written when a factory names a part: `dependsOn` exactly the
  modules the factories name, `uses` `jobs` and the systems they name, and in `create` calls
  `deps.jobs.provide(<factory>, { <dep>: deps.<part>, … })` per factory. Typed: a factory whose dependency is not the
  part's type does not compile. It has a `stop` that stops the jobs engine: it is created last, so it stops first,
  and no step is left running against a module that has already stopped. (`jobs`' own `stop` then finds it stopped.)
  A wiring-lane review (codegen-targets-35) chose this over a late lookup in the wiring, which would hide a dependency
  the typed registry checks today. No module depends on `jobDeps`, so it cannot form a cycle; a domain module that
  starts a run uses the `jobs` system.
- **The bridge on the events system.** With bridge installed, `events` `uses: ['database', 'jobs']` and builds
  `new BridgeOutboxDrainer(jobs.starter, bridgeRegistry)`, checks it (`assertTriggersRegistered`) and passes it to
  `DrizzleEventBus` as the bridge hook. The drain then starts each trigger's run in the event's own transaction (a
  savepoint per trigger), the run's trigger is `event`, and the executor's open-run sweep picks it up after the commit.
- **Generated files under pattern-stack.** The job registry (`<generated>/jobs.ts`) and the bridge registry, through
  the Nest-free entries. YAML jobs (`definitions/jobs/*.yaml`) emit `define<Type>Job(arms)` and the emit-once
  `jobFactory` as under Nest; the detection type comes from the integration entry the wiring selects.
- The subsystem schema barrel carries the job tables and `bridge_delivery` to drizzle-kit, through the `core` entries.
- `jobs-system.ts` and `job-deps.ts` are stale wiring files once jobs is uninstalled, or under nest.

## Not in this step

- **`publishAndStart` (Tier 2).** `EventFlowService` is Nest's; under pattern-stack a caller writes the event and starts
  the run in one transaction itself (`starter.start(…, tx)`). A plain facade comes when an app needs it.
- **The BullMQ executor**, and so `REDIS_URL`.
- **The operator view** (`JobsService`): it is the package's Nest service.
- **J-3** (`ctx.step` sub-steps, durable approvals).

## The gate

- Part 1: unit tests for `JobRunStarter` (moved from `job-starter.spec.ts`; the Nest class keeps a test that it is
  the same starter), `createJobsEngine` over `MemoryJobStore` (a plain job and a factory with provided deps run to
  completion; a factory with no provided values stops `start` naming the job and the dependency; the limiter check;
  `stop` is idempotent), `BridgeOutboxDrainer` (the drain-hook spec runs against both classes), the install's refusal
  and file filter, the `jobs.worker` setting (pattern-stack only), and the Nest-free gate over both new entries plus the
  vendored closure of each install. The Nest output is held by the baseline, the goldens and every Nest smoke;
  `test-jobs-integration` holds the Nest engine.
- Part 2: `test-smoke-pattern-stack` installs jobs and bridge after events and integration. In a project with no Nest
  installed, an `invoice_created` event starts a job through a `jobTriggers` trigger and its steps complete; then a job
  whose step blocks is started, the process is killed mid-step (SIGKILL, no stop), and a second process composes,
  starts, sweeps the open run after its lease expires, and completes it.
