# S-3: integrations under `wiring: pattern-stack`

**Status:** implemented (part 1: the runtime and the `integration` system; part 2: the generators) ·
**Follows:** S-1 · **Plan:** codegen-targets `docs/PLAN-platform-lane.md` §2 (Integrations)

## Problem

PW-3a refused `surface:` under pattern-stack wiring, and S-1 refused `subsystem install integration`.
- **Runtime.** The integration orchestrator (`ExecuteIntegrationUseCase`) takes its parts through Nest tokens
  (`@Inject`, `@Optional`) and logs through Nest's `Logger`. The differ, the cursor stores and the run recorders
  are `@Injectable()`; the Drizzle pair `@Inject(DRIZZLE)`.
- **Generated code.** The five integration generators in `src/cli/shared/` emit Nest: the provider module, the
  adapter module and its `@Inject` constructor, the surface registry module, the per-entity assembly module with its
  Symbol tokens, and the change emitter.

S-3 lands in two PRs. Part 1 is the runtime and the substrate. Part 2 is the generators.

## Part 1: the runtime and the `integration` system

### Runtime: one orchestrator, two hosts

- `IntegrationRunner` (`integration-runner.ts`) is the orchestrator, framework-free. Its constructor takes its parts
  in one object, `{ source, cursors, differ, sink, recorder, multiTenant?, emitter? }`, and it logs through the logger
  port. The run flow is the one `ExecuteIntegrationUseCase` had, moved unchanged.
- `ExecuteIntegrationUseCase` is `IntegrationRunner` under Nest's tokens: a decorated subclass whose constructor
  takes the same positional, token-injected parameters as before and passes them to `super`. Nest assemblies provide
  it as a class, so the generated Nest output does not change.
- The differ, the memory cursor store and the memory run recorder lose `@Injectable()` (each is built with `new`).
  The Drizzle cursor store and run recorder lose their decorators too; `IntegrationModule.forRoot` builds them with
  `useFactory` over `DRIZZLE` and the multi-tenant flag.
- `integration/core` exports the runner, the differ and the memory backends. The Drizzle backends are not exported
  from it: a memory install prunes them, so the system imports the selected one by path (as S-1 does for the bus).
- `IntegrationModule.forRoot` calls `useNestLogger()`, so the runner's lines go
  through Nest's logger in a Nest app.
- The Nest-free gate adds both Drizzle backends as entries; `core.ts` reaches the rest.

### `subsystem install integration` under pattern-stack

- Allowed on drizzle or memory. The refusals left are auth and auth-integrations (S-2), jobs and bridge (J-1), and
  events' Redis backend.
- The vendored copy skips `integration.module.ts`, the `index.ts` barrel (it re-exports the module) and
  `execute-integration.use-case.ts` (the one decorated class left). The file filter is now per subsystem.
- The audit schema is the Hygen template's, as under Nest, and the subsystem schema barrel carries its tables to
  drizzle-kit. `entity new` regenerates that barrel when events or integration is installed.
- Vendored detection keys the install on `core.ts` under pattern-stack, as events does.
- The next step it prints names the `integration` system, `...SYSTEMS` in `compose.ts`, and the schema barrel in
  `drizzle.config.ts`.
- Fixed in passing:
  - the install wrote the empty pattern-stack event set for every subsystem; now only for events;
  - the events and integration config blocks wrote `backend: drizzle` whatever `--backend` said, so a memory install's
    system imported the pruned Drizzle backends. The block prints the installed backend (`--backend` to the Hygen
    config action);
  - a memory install pruned `detection-config.schema.ts` with the table schemas. It is a Zod schema `core.ts` exports,
    so it is kept (`NON_TABLE_SCHEMAS`).

### The `integration` system

`<generated>/integration-system.ts`, from `codegen.config.yaml`'s `integration:` block (`patternStackIntegrationInput`):
- `integrationSystem` uses `database` on drizzle, nothing on memory. `create` returns `IntegrationApi`:
  `{ cursors, recorder, differ, multiTenant }`, the Postgres or memory pair, `new DeepEqualDiffer(<differ options>)`,
  and the flag. `IntegrationApi` is the runtime's `IntegrationSubstrate` (integration-runner.ts, exported by
  `core.ts`), not a second declaration. The backend's classes, whether they take the database and the files they come
  from are one row of `INTEGRATION_BACKENDS` (emit-composition.ts); the CLI passes no backend paths.
- It has no start or stop: nothing in the substrate runs on its own.
- `SystemApis` gains `integration: IntegrationApi`; `SYSTEMS` lists it after `events`. Both are printed from one
  ordered list of the generated systems (`generatedSystems`: key, API type, manifest, file), which also writes each
  system's file; a new system is a row of that list.
- `subsystem install integration` under pattern-stack is integration's row of `PATTERN_STACK_SUBSYSTEMS` (S-1's table):
  drizzle or memory, the skipped Nest files, `core.ts` as the entry detection keys on, the next step.
- A run is `new IntegrationRunner({ ...app.system('integration'), source, sink })`.
- `integration-system.ts` is a stale wiring file once the subsystem is uninstalled, or under nest.

### The gate

`test-smoke-pattern-stack` installs integration (drizzle) after events. It asserts the vendored Nest-free closure, and
that no module, barrel or Nest use case was written; that `integration-system.ts` exists; and that `main.ts` composes
`database, events, integration, …`. On Postgres, `crud-check` inserts a subscription and runs an `IntegrationRunner`
on the system's parts, with a stand-in source and sink. It asserts that the run recorder logs the run and that the
cursor store keeps the last cursor.

`events-pattern-stack.test.ts` also walks, for events and integration on each backend, the relative-import closure of
every file the pattern-stack code imports (`core.ts`, and the backends the system imports), and fails on a file the
install's filter drops. It catches the memory pruning above. It also holds the config blocks to the installed backend.

Unit tests: `emit-composition.test.ts` (the system on both backends, the config's flag and differ options, `SYSTEMS`,
`SystemApis`, no system when not installed) and `events-pattern-stack.test.ts` (the refusal, the file filter). The
integration runtime specs hold the Nest use case, and the module spec the factories. The Nest output is held by the
integration-emit goldens and `test-smoke-integration`.

## Part 2: the generators

`entity new` under pattern-stack writes the integration layer as `@pattern-stack/wiring` manifests: providers and a
surface's adapters as systems, the runs as one module. The `surface:` refusal (PW-3a) is lifted. The plan and its
emission are `src/cli/shared/pattern-stack-integrations.ts`; the `integrations` module is the composition's.

### The shape

| Nest (unchanged) | Pattern-stack |
|---|---|
| `providers/<slug>/<slug>.provider.module.ts`: the strategy and client under Symbol tokens | `<slug>.provider.ts` (@generated): the `<slug>Provider` system, calling `<slug>.provider.factory.ts` (emit-once, author-owned), which builds the strategy and the client |
| `<slug>-<surface>.adapter.ts` (emit-once) with `@Inject` tokens, and its adapter module | the same scaffold as a plain class; `auth` and `client` are typed from the factory's interface (`<P>Provider['auth']`) |
| `<surface>-adapters.module.ts` + tokens: the contributions folded under `<SURFACE>_ENTITY_SOURCES` | `<surface>-adapters.system.ts`: the `<surface>Adapters` system — `adapters.<provider>`, and `sources()` folding them (the same fold function, printed by one helper) |
| per (entity, provider) `<entity>-integration.module.ts` + a use-case token; the surface integration module | the `integrations` module (`<backend_src>/integrations/module.ts`): `crm.contact.salesforce` is an `IntegrationRunner` |
| `<entity>.sink.generated.ts` + `<entity>.sink.ts` | the same; the base imports `IIntegrationSink` from the Nest-free entry |
| `<entity>.change-emitter.ts` injecting `TYPED_EVENT_BUS` | the same class, the bus a plain constructor argument (the `events` system's typed bus) |
| `types.generated.ts` | the same |

### Decisions

- **Providers and adapters are systems; the runs are a module.** A sink takes its entity's repository, which a
  context module builds, and a system can't depend on a module. So the `integrations` module `dependsOn` the modules
  holding the integrated entities, and `uses` `integration`, the adapters systems and (for an `emit_changes`
  entity) `events`. A run reads `deps.<module>.repositories.<entity>`, which is the repository class itself
  (`satisfies` keeps the inferred type).
- **The factory is the author's.** `auth.strategy` and `client.class` name classes whose constructors may need config
  (a base URL, a token, a credential reader). Nest resolved those by DI. Here the emit-once factory constructs them, so
  the author passes what they need. A per-connection provider (every surface a read primitive, RFC-0003 R5) has no
  client, as under Nest. Under Nest such a provider's strategy came from the auth subsystem's `STRATEGY_REGISTRY`; here
  the factory builds it, so the integration layer needs no auth subsystem (S-2), in either runtime mode.
- **The adapters are typed by the factory**, not by `IAuthStrategy`, for the same reason: a vendored pattern-stack
  project has no auth subsystem to import that type from yet.
- **An adapter takes a client exactly when its provider has one** (`adapterTakesClient(def)`), whatever the surface's
  entities: the scaffold is emit-once, so its constructor can't follow an entity count that changes after it was
  written. A read primitive builds its per-connection client itself and leaves this one unused (a public field). The
  scaffold's constructor and the adapters system's `new` both read it.
- **The plan owns the layout.** `planPatternStackIntegrations` carries each provider's factory and system file and
  each surface's adapter scaffolds (with their detection), system, typed view and sinks; `emitPatternStackIntegrations`
  walks it, and the composition's `integrations` module imports the same paths. Every path is a function of
  `src/config/integration-layout.ts`; the write helpers, the banner, the scaffold sentinel and the import path are the
  shared ones (`src/utils/generated-file.ts`, `src/utils/import-path.ts`).
- **Stale files under pattern-stack.** A run removes its own generated systems and module that it no longer writes (a
  provider or surface whose YAML went, the module after the last Integrated entity), as well as Nest's; it keeps the
  files this run writes. The other wiring's scaffolds are named only when they start with the scaffold sentinel, and
  a Nest import is found in either quote style.
- **Only providers that serve a surface with a package get a system and a factory.** A provider whose every surface
  is skipped (no `codegen-<surface>`) has nothing to build its parts for.
- **A provider YAML that fails to load is refused** when the composition is written, not dropped from it: `entity
  new`'s pre-flight stops on it, and `junction new` and a dry run now do too.
- **`sources()` folds on demand.** Two providers serving one entity is an ambiguous-source error when it is called,
  not at compose, so an app that never reads the registry boots. Under Nest the registry module was likewise kept
  off the app's graph (RFC-0002 §7 q3).
- **A run whose adapter has no change source yet** is built anyway (the source is `undefined` until the author fills
  `changeSources`), and fails when executed, as the Nest assembly did. A freshly generated project composes.
- **Names.** A provider's system is `<slug>Provider` (camelCased), a surface's `<surface>Adapters`; the module is
  `integrations`. A system that would share a name with a module or system of the composition is refused, and so is
  a context named `integrations` when there are runs.
- **Refusals.** Runs with the integration subsystem not installed name `codegen subsystem install integration`; an
  `emit_changes` entity with events not installed names `codegen subsystem install events`.
- **Runtime.** `IntegrationRunner<T>` no longer requires `T extends Record<string, unknown>` (the protocols never
  did); the projection types are interfaces. `DeepEqualDiffer<T extends object>`, and the system's `differ` is an
  `IFieldDiffer<object>`, which every run's record type accepts.
- **Switching wiring.** Going pattern-stack removes Nest's generated integration modules, tokens files and adapter
  barrels; going nest removes the pattern-stack systems, provider systems and module. Only files with codegen's
  banner. The other wiring's author-owned scaffolds (a Nest adapter; a factory or plain adapter) are named in a
  warning: codegen skips an existing scaffold, so the author ports or deletes it.
- **One text owner.** The adapter scaffold, the sink base and the change emitter take a `wiring` parameter rather
  than having twins; the Nest branches print the same bytes (the integration-emit golden holds them). The surface and
  Integrated-entity filtering (`integrationSurfaces`, `notIntegratedReason`) and the fold function
  (`entitySourcesFold`) are shared by both wirings.

### Not in this step

- A `detection:` entity's integration-source module (ADR-033.1) is Nest's and is skipped (printed), as before.
- The jobs handlers that start integration runs (RFC-0005) come with J-1.
- The `home_automation` surface is S-4.

### The gate

- `test-integration-emit`: a second golden, the pattern-stack tree for the fixture (package mode), asserted free of
  Nest; vendored mode imports only the Nest-free integration entry. The Nest golden is unchanged. The emitted-name
  hygiene gate holds the pattern-stack tree too (its new text names lib globals as `globalThis.<Name>`).
- `test-smoke-integration --wiring pattern-stack` (in `just test-smoke-integration`): the fixture in a project with no
  Nest installed, events and integration installed, plain provider stubs. It asserts no `@nestjs` import and no Nest
  integration file; that the systems, factories, module, sinks and change emitter exist; `tsc` over the whole project;
  and that `main.ts` composes every provider and adapters system and the `integrations` module after the entity module,
  then starts and stops. A usage file reads a run by `crm.contact.salesforce` and an adapter by provider, so the module's
  API is compiled as code uses it.
- Unit tests: `pattern-stack-integrations.test.ts` (the plan, the factory and systems, the plain scaffold, sink and
  emitter), `emit-composition.test.ts` (the module, `SYSTEMS`, `MODULES`, the refusals) and
  `stale-integration-files.test.ts` (the switch both ways).
