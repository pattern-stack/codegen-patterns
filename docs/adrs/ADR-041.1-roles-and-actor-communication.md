# ADR-041.1 — `roles:` and the `Actor` / `Communication` library capabilities

**Status:** Accepted
**Date:** 2026-09-17
**Related:** ADR-041 (capability composition emission — this is its first library consumer), ADR-042 (repository
tenant scoping), ADR-044 (the relation graph as the read contract)
**Extends:** ADR-041 §3 (`kind: 'capability'`), §5 (migration scope), §6 (config hand-off)
**Specs:** `docs/specs/CAP-2.md` (the `roles:` block), `docs/specs/CAP-3.md` (the capabilities)

## Context

ADR-041 §5 named `Group` / `Individual` as the first capabilities to ship. The relations-v2 plan (PLAN §6) folded that
lattice into two capabilities with a declaration between them:

- a communication-style entity (meeting, email, message) is an interaction with **actors in roles** — `host`,
  `attendees`, `about`;
- an actor is an entity a role may point at, and is either one actor or a group of them.

CAP-2 shipped the `roles:` block and validated it by capability *name*; CAP-3 ships the capabilities. Building them
settled several things ADR-041 did not decide.

## Decision

### 1. `roles:` is the declaration; `Communication` reads it

A role is a top-level `roles:` entry (CAP-2): `cardinality: one` derives a `belongs_to` keyed by the role name,
`cardinality: many` names a junction. `roles:` and `Communication` imply each other, and every role's `target` must
declare `Actor`. The block has no second home: `Communication` takes **no** `config:`, because its configuration
*is* `roles:`.

### 2. Library capabilities get a **resolved** config, not a copied one

ADR-041 §6 hands a capability its `config:` block verbatim. That is enough for a capability whose config is plain
data, and not for these two: their mixins need Drizzle tables and column keys, and the YAML names roles, junctions
and relationships. Codegen resolves those names at generation time and emits the result on the repository:

- `communicationConfig = { roles: { <role>: { cardinality: 'one', target, column } | { cardinality: 'many',
  target, via: { table: <junction table>, self, target } } } }`;
- `actorConfig = { kind: 'individual' } | { kind: 'group', members: { table: <member table>, foreignKey } }`, where
  `members:` names one of the entity's own `has_many` relationships.

Tables are emitted as **live, typed handles** (imported into the repository), not strings. There is no import cycle
(the junction and member modules import entity files, never a repository). An app capability still receives its
config verbatim.

### 3. One statement each, scoped at the repository

- `findByRole(role, actorId)` → one `SELECT` through the repository's `baseQuery()`. A many-role is an `EXISTS`
  over the junction inside that scoped `WHERE`.
- `participants(id)` → `{ role, target, id }[]`, **ids only**, from one `UNION ALL`. Every branch is under
  `scopeAnd()`; a many-role branch joins the junction back to this table so the scope applies. Hydration belongs to
  the relation graph's typed includes (ADR-044), not to a second mechanism here.
- `memberPredicate(actorId)` (`Actor`) is a predicate **over the actor's own table**: "this row is, or contains,
  `actorId`". It is the identity for an individual; for a group it is an `EXISTS` over the member table. A predicate
  over the *member* table would only be usable from another repository, which the one-statement rule forbids, and it
  would carry none of that entity's scope. `memberPredicate` returns a Drizzle `SQL` fragment, so it is not
  forwarded to the service. `findByRole` and `participants` are forwarded.

None takes a scope parameter (ADR-042).

### 4. A pattern name is unique across library and app patterns

Before this, `getPattern()` looked up app patterns first and the loader checked duplicates only among app patterns.
So a project's `Actor` would have silently replaced the library one. An app pattern that reuses a library name is
now a **load error**, and the pattern is not registered. This is the same rule that already applied to two app
patterns with one name, and there is no override flag. The CLI registers the library before loading app patterns so
that the check can run.

### 5. Runtime-shipped mixins annotate their return type

A mixin in `runtime/` is compiled with declarations. TypeScript cannot emit the anonymous class type of a mixin
whose base has `protected` members, and every repository base does (TS4094). Library mixins therefore return
`TBase & CapabilityCtor<Surface>`, where `Surface` is an exported interface. An interface has no `protected`
members, so a library mixin's config property is public. The generated repository emits every capability config as
`override readonly`, which also overrides a consumer mixin's `protected` declaration.

## Consequences

- The capability smoke's fixture uses the library capabilities in both runtime modes; the stand-ins are gone.
- A `roles:` edge is now queryable in both directions: the generated service's `host(meetingId)` (CAP-2, role-keyed
  relations) and `findByRole('host', contactId)`.
- `findByRole`'s `role` is typed to the declared role names (`RoleOf<this>`), on the repository and through the
  generated service forwarder. That is reachable only because §5 made the config public: indexing a `protected`
  member on a type parameter is TS4105.
- `memberPredicate`'s member hop is a membership test on the FK. It returns no member rows and does not apply the
  member entity's soft-delete or tenant scope, because the one-YAML emitter does not have that entity's
  declaration. Per-hop scope arrives with the relation graph's include trees.

## Alternatives considered

- **Keep app/library shadowing.** Rejected: a silent override of a library capability is exactly the kind of quiet
  divergence the no-backwards-compat rule exists to prevent, and nothing depends on it.
- **A `sql` fragment built from junction table/column name strings.** Rejected in favour of live handles: they are
  typed, need no quoting logic, and the cycle that would have justified strings does not exist.
- **Dual-authoring `Activity` as a capability** so a meeting can be `[Integrated, Activity, Communication]`.
  Deferred per ADR-041 §5: no consumer needs it yet.
