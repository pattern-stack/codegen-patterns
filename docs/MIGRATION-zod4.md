# Migrating a generated app to Zod 4 (codegen 0.35.0, ZOD-1)

From 0.35.0 the code codegen generates and vendors is Zod 4: the DTOs, `ListQuerySchema`, `ZodValidationPipe`, the
OpenAPI registry, the event payload schemas and the integration detection schema. An app generated by 0.34.x or
earlier is on Zod 3. To upgrade it:

## 1. Dependencies

```bash
bun add zod@^4.6.7 @pattern-stack/codegen@^0.35.0
bun remove @anatine/zod-openapi        # the OpenAPI registry no longer uses it
bun add @pattern-stack/query-surface@^0.4.0   # only if you use it: 0.4.0's zod peer is ^4
```

## 2. Regenerate

```bash
codegen update                 # re-vendor runtime/ (pipe, registry, pagination) and installed subsystems
codegen entity new --all       # every DTO is rewritten
codegen junction new --all     # if you have junctions
```

Nothing in your YAML changes.

## 3. What changes for clients of the generated API

- **400 bodies carry Zod 4's issue codes and messages.** The body's shape is the same:
  `{ statusCode, error, message, issues: [{ path, code, message }] }`. Some `code`s are renamed, as is Zod 4's own
  wording:

  | Zod 3 `code` | Zod 4 `code` |
  |---|---|
  | `invalid_enum_value` | `invalid_value` |
  | `invalid_literal` | `invalid_value` |
  | `invalid_string` | `invalid_format` |
  | `invalid_union_discriminator` | `invalid_union` |
  | `not_multiple_of` | `not_multiple_of` (unchanged) |

  A message such as `Expected string, received number` reads `Invalid input: expected string, received number`. A
  client that switches on `code`, or matches `message` text, needs these.
- **ids are checked as `z.guid()`:** any 8-4-4-4-12 hex string, as Postgres `uuid` accepts. It was
  `z.string().uuid()`, which Zod 4 makes strict (RFC 9562 version and variant bits); codegen did not take that
  change, so ids other systems minted keep passing.
- **A `required: true` `json` field must be sent on create.** Its schema is `z.unknown()`, and Zod 3 let an
  `unknown` key be absent; Zod 4 requires it. Send the field (`null` is a value), or make it not `required`.
- **A PATCH never fills a default.** That was already so on Zod 3 (0.34.x ignored a default under `.optional()`), and
  0.35.0 keeps it on Zod 4 (ZOD-1a). Leaving a field out leaves it as it is.
- **`/docs-json`** is built by Zod 4's `z.toJSONSchema` (OpenAPI 3.0 target). It has the same paths and schema names;
  the JSON details differ. A date is `type: string, format: date-time`, as it was before.

## 4. Code you wrote against the generated schemas

Where your own code uses Zod 3 APIs on generated or vendored schemas, update it. These are the patterns seen in
generated apps; Zod's own guide covers the rest (https://zod.dev/v4/changelog):

| Zod 3 | Zod 4 |
|---|---|
| `error.errors` | `error.issues` |
| `{ errorMap }`, `{ invalid_type_error, required_error }` | `{ error: (issue) => … }` |
| `ZodEffects`, `schema._def.innerType` | `ZodPipe` / `.unwrap()`; schemas from `.transform()` are pipes |
| an object `.default({})` that should fill inner defaults | `.prefault({})` |
| `z.record(valueSchema)` | `z.record(z.string(), valueSchema)` |
| `.strict()` / `.passthrough()` | `z.strictObject(…)` / `z.looseObject(…)` (the old forms still work) |
| `import type { ZodIssue, ZodSchema } from 'zod'` | `z.core.$ZodIssue`, `z.ZodType` |
| a `z.unknown()` key meant to be optional | `z.unknown().optional()` |

Your app-defined patterns (`src/patterns/*.pattern.ts`) need no change: codegen reads a pattern's `configSchema`
through a structural type, so a Zod 3 or Zod 4 schema both work.
