# Jobs

Durable background work runs on **`@pattern-stack/jobs`** (JOBS-3). A **job** is a value you declare in code
(`defineJob`): a key, a zod input and output, and its steps in order. A **run** is one durable execution, stored in
your app's Postgres; a **step** is one recorded stage, so a resumed run never redoes a finished step. The executor
runs in your process (or in `src/worker.ts`), sweeps for open runs, and leases each one, so two replicas never
advance one run at once.

The engine's full contract ships with the package: `node_modules/@pattern-stack/jobs/JOBS_CONTRACT.md`. This skill
covers the app side codegen generates.

## Non-obvious rules

- **A job is registered by being exported** from a file under `<backend_src>/jobs/`. Run `codegen entity new` after
  adding one; the generated `jobs.ts` lists it. Two exports with the same name are a generation error.
- **Start runs with `JobStarter`** (`start(key, input, opts, tx?)`), injected by class. Pass `tx` to create the run
  in your transaction: it commits with your writes, and the executor's sweep picks it up after the commit.
- **A step names its pool as a limiter**: `step({ limiter: 'batch', run })`. `interactive` (20) and `batch` (5)
  always exist; a step naming a pool the config doesn't declare stops the boot.
- **Every value is plain JSON** (input, step outputs, item results), at most 1 MB: no `Date`, `Map`, class
  instances. Send a time as an ISO string.
- **A step's code runs in the run's tenant scope**: every entity-repository read and write inside it is scoped to the
  run's tenant, as superuser on the user axis. `SYSTEM_TENANT` (no tenant named) is the null tenant partition.
- **A job with no `limits` needs a budget at the start** (`budget.maxItems`); give public or bridge-started jobs
  `limits`.
- **Determinism:** a step reads its input and earlier outputs, never the clock or randomness to decide what work to
  do; bump `version` when a step's code changes what an open run would compute.

## Do not

- Do not write `@JobHandler` classes, inject `JOB_ORCHESTRATOR`, or register `JobsDomainModule` / `JobWorkerModule`:
  that subsystem (ADR-022) is gone. `docs/MIGRATION-jobs-engine.md` in the codegen package maps old to new.
- Do not register `JobsEngineModule` in `app.module.ts` by hand; `SUBSYSTEM_MODULES` composes it.
- Do not create a table per job. A job's values live in the job tables; domain data goes to its domain's tables,
  written by a step.
- Do not reach for a job when the caller waits synchronously on the result — that is a use case.

## Under `target.wiring: pattern-stack` (no Nest)

- `codegen subsystem install jobs` vendors the Nest-free entry (`@shared/subsystems/jobs/core`) and writes no
  `worker.ts`; `codegen entity new` writes the `jobs` system (`<generated>/jobs-system.ts`). Start a run with
  `app.system('jobs').starter.start('<key>', input, opts, tx?)`; read runs through `app.system('jobs').store`.
- The executor runs in every process whose `JOBS_WORKER` is `true` (the default; `codegen project settings` lists it).
  An HTTP or CLI process that only starts runs sets it `false`, and a worker's open-run sweep takes them.
  `jobs.worker_mode` is not read.
- A job factory's dependencies are composition parts: `injected<CrmModule>('crm')`, `injected<IntegrationsModule>('integrations')`,
  `injected<EventsApi>('events')`. The generated `jobDeps` module provides them, typed by the factory (a wrong part does
  not compile). A class token is refused: there is no container to resolve it by.
- `jobs.lease_ttl_ms` is how long a crashed process's run waits before another process resumes it (default 60 s).
- Spec: `docs/specs/J-1.md` in the codegen repo.
